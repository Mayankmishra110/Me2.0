# M2-103 — Durable job queue and worker pool

## What was built
`internal/queue` implements a durable SQLite-backed job queue on the existing `jobs` table: `Register` /
`Enqueue` (with `RunAt`/`Priority`/`Parent`/`ContentID`), `Permanent(err)`, atomic claim with 5‑minute
leases and 60 s heartbeats, backoff retries (1m/5m/30m/2h) then dead-letter + `events` alert, crash
recovery via `RecoverExpiredLeases`, and resource-class worker pools (heavy/light/net) that skip claiming
while paused globally or per class.

Deviations from ARCHITECTURE / SPEC / DESIGN:
1. **"per agent" pause** scoped to per-resource-class (`pause:resource:heavy|light|net`) plus `pause:all` —
   ticket only owns resource-class pools; recorded in ticket Notes.
2. **`failed` vs `dead`**: `Permanent(err)` → `failed` (no alert); max_attempts exhaustion → `dead` + alert.
3. Claim atomicity relies on `internal/db.Open` `SetMaxOpenConns(1)` plus `UPDATE…RETURNING` (no cgo/`-race`).

## Known gaps and follow-ups
- No caller yet wires `Register` / `StartWorkers` / `RecoverExpiredLeases` into `cmd/mayank2` — daemon
  startup is out of `touches: [internal/queue/]`; next consumer should call `RecoverExpiredLeases` once
  before `StartWorkers` and size pools from `config.QueueConfig`.
- Scanning SQLite `TEXT` JSON into `json.RawMessage` fails on this toolchain; `scanJob` works around via
  `string` → `json.RawMessage`. Future packages scanning JSON TEXT columns will hit the same issue.
- Per-job-type / per-channel pause (if wanted) belongs in httpapi/telegram tickets, not here.
