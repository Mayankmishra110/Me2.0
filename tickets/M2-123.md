## Goal
M2-122 fixed Instagram/Facebook/Pinterest to presign real R2 URLs (`Presign`
field) instead of a stub, but nothing ever uploaded a finished render to R2 —
so with real credentials, presigning succeeds but the object doesn't exist
and publishers get a 404. This ticket closes that gap: renders are uploaded
to R2 as part of the render pipeline, and publishers resolve the real R2 key
recorded for each asset instead of guessing from the local path.

## Design decision
**Option (a): upload at render-finalization time, not lazily at publish
time.** `content.Renderer.recordFile` (internal/content/render.go) uploads
each `render`/`thumb` kind asset to R2 right after it's written locally
(when `Renderer.R2` is configured) and stores the resulting key in the new
`assets.r2_key` column. `publish.AssetR2KeyResolver`
(internal/publish/r2resolver.go) is a read-only lookup: given
`(contentID, videoPath)` it finds the `assets` row for that content whose
`path` has the same filename and returns its `r2_key` — a cheap indexed
`SELECT`, not an "upload if missing" lazy path. Chosen over lazy
upload-at-publish-time because:
- The render job already has the file open and hashed (`media.DigestFile`)
  moments before this point, so uploading here is one extra network call
  with no extra disk I/O, vs. publish time re-reading/re-opening the file
  from a worker that otherwise has no reason to touch local media I/O.
- A publish attempt failing on a missing `r2_key` (R2 configured but this
  particular asset was never rendered with R2 on) is a clear, immediate
  signal at presign time — no different from the lazy design's behavior
  when the upload-on-demand path fails — but the common case (R2 on for the
  whole run) never pays an upload latency cost inside the publish job,
  which already has its own per-platform timeouts to worry about.
- Keeps "produce the asset" and "make it reachable" as one step owned by
  the renderer, rather than splitting R2-upload responsibility across two
  packages (content and publish) that would each need to handle upload
  failure/retry semantics.

`Renderer.R2 == nil` (R2 not configured, CONTEXT D24) means renders stay
local-only and `r2_key` is never set; publishers' existing nil-safe
fallback (use `VideoPath`/`ThumbnailPath` literally as the key) is
unchanged, and `AssetR2KeyResolver` itself also degrades cleanly (nil DB,
empty content_id, or no matching r2_key all return `"", nil` — never a
fabricated key, never an error that would block the no-R2 path).

## Gap found and fixed in this session
The in-progress work (before a rate-limit interruption) wired
`R2KeyResolver` into `Instagram` and `Facebook` but not `Pinterest`, even
though Pinterest's cover image (`ThumbnailPath`) goes through the same
`Presign` flow as the other two (`Pinterest.resolveCoverURL`). Pinterest
would have kept presigning `req.ThumbnailPath` literally instead of the
real uploaded `r2_key`, silently defeating this ticket's fix for that one
platform. Added the `R2KeyResolver` field to `Pinterest` (matching
Instagram/Facebook's signature and nil-safe fallback) and wired it in
`resolveCoverURL` and in `cmd/mayank2/registerPublishHandlers`.

Also confirmed (not a gap, just verified): `internal/publish/r2resolver_test.go`
already used the real `mustExec`/`openPubDB` test helpers from
`internal/publish/youtube_test.go` with matching signatures — it compiled
and passed as-is once the rest of the package built.

## Review

Independent qa/sec re-review in `data/worktrees/m2-123`, re-derived from real code, not the build report.

**Rebase.** Branch was 1 commit ahead / 5 behind `origin/main` (M2-122's merge at `9240be8` had landed
since this branch was cut). `git fetch origin && git rebase origin/main` hit one real conflict in
`cmd/mayank2/run.go`'s `registerPublishHandlers` region — expected overlap with M2-122, which also touched
this function. `origin/main`'s version built its own `*storage.R2Client` internally via a local
`buildPresigner(log)` helper (no shared client); this ticket's version needed `registerPublishHandlers` to
*accept* a `r2Client *storage.R2Client` parameter instead, so the same client built once in `cmdRun` could
be shared with `content.Renderer.R2` (the upload side) and `publish.AssetR2KeyResolver` (the read-back
side). Resolved by keeping this ticket's signature/wiring (the superset — it still presigns and now also
resolves `r2_key` and shares the client), removing the now-redundant `buildPresigner` function and its
duplicate `publishPresigner`/`notConfiguredPresigner` type definitions that a naive resolution would have
left declared twice, and fixing one stale comment that still referenced the removed `buildPresigner`.
`cmdRun`'s own r2Client-construction block (added by this ticket, not touched by M2-122) auto-merged
cleanly. Post-rebase tip is `190af92`. No product-behavior conflict — purely a rebase mechanic between two
tickets that both touch the same wiring function — so nothing needed escalating to Mayank.

**1. Eager upload in render.go.** Confirmed `Renderer.recordFile` (`internal/content/render.go:575-613`)
uploads `render`/`thumb` kind assets (`uploadKinds` map, not `voice`/`subs`) to R2 via `r.uploadToR2` right
after the local write, only when `r.R2 != nil`. The resulting key is stored in `assets.r2_key` via a real
`INSERT` column (`r2KeyArg` is `nil` when empty, so the column stays SQL NULL rather than an empty string —
correct, since `AssetR2KeyResolver`'s query filters on `r2_key IS NOT NULL AND r2_key != ''`). Upload failure
(`uerr != nil`) logs a `Warn` and falls through with `r2Key` left `""`; the function still returns the asset
and `nil` error — a transient R2 outage cannot fail the render job. Verified this isn't just a code-reading
claim: added `TestRecordFile_UploadFailureLogsAndContinues` (new, see below) which points `r.R2` at an
`httptest` server returning 500 and asserts `recordFile` returns no error and `r2_key` stays NULL in the DB.

**2. Migration check.** No new migration file exists for `r2_key` — correctly, because none was needed.
`grep -n r2_key migrations/*.sql` shows it's already a column on `assets` in `migrations/001_init.sql` line
68, committed in `280939d0` (M2-102, 2026-09-28), long before this ticket or even M2-122 existed.
`git diff main...m2/M2-123 -- migrations/` is empty — this branch makes zero migration changes. So this is
a real, verified pass: the code references a column the schema has always had, not a silently-assumed one.

**3. `AssetR2KeyResolver`.** Confirmed genuinely read-only (`internal/publish/r2resolver.go`): a single
`SELECT path, r2_key FROM assets WHERE content_id = ? AND r2_key IS NOT NULL AND r2_key != ''`, no `INSERT`/
`UPDATE` anywhere in the file — the report's claim that it deviated from the brief's option (b) (lazy
upload-at-publish-time) is correct and is the right call per the ticket's own Design decision section
(upload-time already has the file open/hashed; publish-time would mean re-opening local media I/O from a
worker that has no other reason to touch it). Disambiguates multi-asset-per-content_id by
`filepath.Base(videoPath) == filepath.Base(row.path)`, iterating rows `ORDER BY id DESC` and returning the
first filename match — correctly handles a content_id with both `long.mp4`/`short.mp4` renders and a
`thumb.png`. Degrades to `("", nil)` for: nil `db` (line 46), empty/whitespace `contentID` (line 46, checked
before any query), and no filename match after exhausting rows (line 72) — all confirmed by the existing
`r2resolver_test.go` (5 tests, re-run individually, all pass) plus general suite.

**4. Pinterest fix — most important check.** Confirmed via `git show 9240be8:internal/publish/pinterest.go
| grep R2KeyResolver` → no match: at `9240be8` (main after M2-122 merged), Pinterest had `Presign` wired but
**no `R2KeyResolver` field at all** — a real, pre-existing gap this ticket closes, not a false claim.
Current `pinterest.go` (`internal/publish/pinterest.go:60-63,213-221`) now has the field and
`resolveCoverURL` uses it with the identical nil-safe pattern Instagram (`instagram.go:175-176`) and
Facebook (`facebook.go:186-187`) use: call resolver only `if p.R2KeyResolver != nil`, and only overwrite
`key` `if strings.TrimSpace(k) != ""`, so a resolver miss falls through to the literal `ThumbnailPath`
exactly as before. Wired in `cmd/mayank2/run.go`'s `registerPublishHandlers`, sharing one `resolveR2Key :=
publish.AssetR2KeyResolver(sqlDB)` across Facebook/Instagram/Pinterest — confirmed post-rebase, this wiring
survived the `run.go` conflict resolution intact (see Rebase note above).

**5. D24 degrade path, traced for real.** With `R2_*` env unset, `storage.NewR2FromEnv` in `cmdRun` returns
a `*NotConfiguredError`, `r2Client` stays `nil`, and that `nil` is passed into both
`registerComplianceAndContent` (→ `Renderer.R2 = nil`) and `registerPublishHandlers` (→
`presign = notConfiguredPresigner{...}`, `resolveR2Key := publish.AssetR2KeyResolver(sqlDB)` — note
`sqlDB` itself is never nil here, only `r2Client` is, so this resolver is DB-backed but will simply never
find any `r2_key` rows since none were ever written). Traced `recordFile`: `r.R2 != nil` is false, so
`uploadToR2` is never called, `r2Key` stays `""`, and the `INSERT` writes SQL NULL. Traced
`AssetR2KeyResolver`: the `WHERE r2_key IS NOT NULL` filter means it can never match any row when nothing
was ever uploaded, so it always falls through its loop to `return "", nil`. Both publishers' existing
nil-safe fallback then uses `VideoPath`/`ThumbnailPath` literally, unchanged from pre-ticket behavior. Added
`TestRecordFile_NoR2ConfiguredLeavesR2KeyEmpty` (new) to assert this end-to-end at the DB row level, not
just by inspection.

**6. No secrets in the new upload log line.** `recordFile`'s failure log (`render.go:592`) is
`r.log().Warn("content render: r2 upload failed, asset stays local-only", "content_id", contentID, "kind",
kind, "path", filePath, "error", uerr)` — fields are content_id/kind/local path/error only. `uerr` comes
from `(*storage.R2Client).Upload`, which wraps the AWS SDK's `PutObject` error with `fmt.Errorf("storage: r2
upload %s: %w", key, err)` (`internal/storage/r2.go:170-172`) — `key` is the R2 object key (not a secret),
and the AWS SDK's own PutObject error does not embed the request's signing credentials or a presigned URL.
Confirmed by triggering a real upload failure in the new test and inspecting the actual log line emitted
(reproduced above) — no `Authorization` header, access key, or presigned URL text appears in it.

**Test gap found and fixed.** `internal/publish/r2resolver_test.go` covered the resolver well, but

upload-succeeds and upload-fails-and-continues paths had zero direct test coverage — only implied by code

real key both in the returned `recordedAsset` and the `assets.r2_key` DB column, via a real `httptest`
server through `storage.NewR2`, no network/credentials), upload-fails-logs-and-continues, and
R2-not-configured-leaves-r2_key-empty. This is a small, in-scope addition (`internal/content/render.go` is
already in this ticket's `touches`), not a new gap left open.
