## Goal
Mayank decided (2026-10-01, CONTEXT D28) the product must run on a single
Gemini API key with no Ollama installed on this machine. Every LLM task
(research/script/metadata/classify/translate_cleanup) routes to Gemini when
it's the only configured provider, and the G2 compliance originality gate
gets a real, working embeddings path via Gemini's OpenAI-compatible
`/embeddings` endpoint instead of silently depending on a local Ollama
model that no longer exists on this machine.

## Ollama dependencies found and how resolved
1. **`internal/llm.Router.Embed`** previously hard-coded a search for a
   `*ollamaProvider` in the router's provider list and returned
   `ErrNoProvider` if it wasn't reachable — there was no way to embed via
   anything else, Ollama or not. **Resolved:** `Embed` now runs through a
   normal routed chain (`config.llm.routes.embed`, new `TaskEmbed` route
   name) exactly like `Complete`/`CompleteWithSchema` — first available,
   embedding-capable provider wins, falls through on `ErrUnavailable` with
   the same quota/backoff bookkeeping. (`internal/llm/llm.go`)
2. **`openaiCompatProvider`** (used for Gemini, Groq, Cerebras, OpenRouter)
   had no `Embed` method at all — only `ollamaProvider` could embed.
   **Resolved:** added `(*openaiCompatProvider).Embed`, calling
   `POST {base_url}/embeddings` with the provider's `embed_model`
   (new `ProviderConfig.EmbedModel` field, already existed for ollama, now
   also read for openai_compat). Verified 2026-10-01 against
   `ai.google.dev/gemini-api/docs/openai` (documents `/embeddings` alongside
   `/chat/completions`) and `ai.google.dev/gemini-api/docs/embeddings`
   (`gemini-embedding-001` is the current model id). Any openai_compat
   provider with `embed_model` set can serve embeddings this way, not just
   Gemini. (`internal/llm/openai.go`)
3. **`config/config.example.yaml`**: `llm.routes.embed` did not exist as a
   named route — embeddings were implicitly "whatever Ollama is." Added
   `embed: [ollama, gemini]` (Ollama first when installed/cheaper-local,
   Gemini otherwise) and added `embed_model: "gemini-embedding-001"` to the
   `gemini` provider entry. `metadata`/`classify` routes previously had no
   fallback past `[ollama, groq]` — with neither installed/keyed, those
   tasks had no route at all on a Gemini-only machine; appended `gemini` to
   both. `research`/`script`/`translate_cleanup` already listed `gemini`
   in their chains. `claude` stays excluded from every content route
   (research/script/metadata/classify/translate_cleanup) per CLAUDE.md
   ("Claude is for Builder and blog only") — only `blog`/`builder` routes
   use it.
4. **`cmd/mayank2/doctor.go`** had a generic Ollama-reachability check but
   nothing that reported embeddings specifically — an operator with no
   Ollama and no Gemini key configured for embeddings would see no signal
   at all that G2 was about to fail closed on every script. Added
   `checkEmbedRoute`, which resolves `llm.routes.embed` the same way the
   router does and reports which provider it actually lands on. Ollama not
   running is ⚪ (`checkOllamaProvider`, pre-existing, unchanged — optional
   local model, D24), never ❌.

## Was any gate found silently passing before this fix?
**No.** Read `internal/compliance/g2.go` as it stood before this session's
changes (via `git show HEAD:...` and the Notes below): `G2.scriptVector`
already returned a hard error — not a pass — whenever `g.Embed` was nil or
returned an error/empty vector *and* `item.PriorEmbeddings` was non-empty
(`TestG2_priorsWithoutEmbedFailsClosed`, `TestG2_emptyEmbedAgainstPriorsFailsClosed`,
both pre-existing tests, unmodified in intent). So G2 already failed closed
on "no embedder at all." What was missing, and what this ticket actually
fixes, is narrower but still real:
- There was **no way to get a working embedder in the first place** on a
  Gemini-only machine (Ollama dependency #1/#2 above) — so on this machine,
  before this fix, G2 would have failed closed on *every single script*,
  permanently, not a silent pass. The risk was total unavailability of the
  originality check, not a false pass.
- **Cross-model vector comparison was a latent, unexercised risk, not yet a
  bug that had shipped a false result**, because only one embedding model
  (`nomic-embed-text` via Ollama) had ever existed before this ticket — there
  was nothing to mix yet. But the moment a second model (Gemini) was added
  as a fallback, comparing its vectors against old `nomic-embed-text` rows
  by raw cosine similarity would have produced meaningless scores (different
  dimensionality/semantics) that could register as a false "near duplicate"
  or a false "distinct" — a real future gate weakening if left unguarded.
  Fixed proactively in this same change: `script_fingerprints` gained an
  `embed_model` column (migration below), `PriorEmbedding` now carries
  `{Vector, Model}`, and `G2.Check` only computes cosine between vectors
  sharing the same model — a mismatched-model prior is skipped (and noted
  in the gate's `Detail`), never compared, never treated as a pass or a
  fail on its own. Proven by `TestG2_crossModelPriorsSkippedNotCompared`.

## Embedding design
- `llm.Router.Embed(ctx, EmbedRequest)` now routes through
  `config.llm.routes.embed` like any other task: walks the chain, skips
  unknown providers, skips provider kinds that don't implement the new
  `embedProvider` interface (`claude_cli` — proven by
  `TestEmbedSkipsNonEmbeddingProvider`, no panic, no silent pass), skips
  unavailable providers (quota/backoff), calls `Embed`, falls through to
  the next candidate on `ErrUnavailable` with the same backoff bookkeeping
  `Complete` uses. Exhausting the chain returns `ErrNoProvider` wrapping
  every per-candidate error (`TestEmbedNoProviderAvailable`,
  `TestEmbedRouteMissing`) — fails closed, same error type G2 already
  treats as fatal.
- `EmbedResponse.Model` is always the real model that produced the
  vectors (`firstNonEmpty(out.Model, requestedModel)` — prefers what the
  API echoes back, falls back to what was requested if the API omits it,
  never fabricated).
- `compliance.RouterEmbedder.Embed` and `compliance.Engine.saveFingerprint`
  both now thread that model id through: every new `script_fingerprints`
  row is written with the real `embed_model`, and `G2.Check` receives it
  alongside the freshly computed vector so it can filter `PriorEmbeddings`
  by matching model before touching cosine similarity at all.
- `migrations/003_fingerprint_embed_model.sql`:
  `ALTER TABLE script_fingerprints ADD COLUMN embed_model TEXT NOT NULL
  DEFAULT 'nomic-embed-text'` — append-only (001/002 untouched), existing
  rows (all produced by the only model that ever existed before this
  ticket) default correctly, new rows always write their real model.
- `G2MaxCosine`/other thresholds (COMPLIANCE §3) were tuned for
  `nomic-embed-text` and have **not** been re-tuned for
  `gemini-embedding-001` — flagged as an open question in CONTEXT.md §5
  rather than guessed at, since changing a compliance threshold is a
  product-behavior decision, not an implementation detail.

## Fix for QA finding #5 (2026-10-04)

Addressed the reviewer's finding directly: `checkEmbedRoute`
(`cmd/mayank2/doctor.go`, was line ~307) returned `offResult` (⚪, exit 0)
when `llm.routes.embed` is non-empty but every candidate in it is
unavailable right now (no Ollama running *and* no Gemini key set — the
exact fresh-machine case this ticket targets). The reviewer correctly
pointed out this has the identical real-world consequence as the
missing-route case, which is already (and remains) `brokenResult` (❌):
G2 fails closed on every script, permanently, until someone notices.

**Where the ⚪/❌ line now sits, and why:** the final `return` in
`checkEmbedRoute` — reached only after the loop has tried every name in a
*non-empty* chain and found none ready — now returns `brokenResult`
instead of `offResult`, unconditionally. I considered narrower options
(e.g. only flip it for the "no key" reason, keep ⚪ for "no embed_model
configured") and rejected them: every reason a candidate gets skipped in
that loop (unknown provider, no `embed_model`, unreachable Ollama, no
API key, unsupported kind) produces the exact same downstream effect once
the *whole chain* is exhausted — zero working embedder, G2 permanently
fails closed. There is no reading of "exhausted but fine" for this
specific aggregate check. So I did not stop at the reviewer's minimum
suggestion ("at least flip the no-key case") and instead made exhaustion
of a non-empty chain always ❌, for any reason.

This also meant updating a second, previously-passing subtest that the
reviewer didn't call out by name: `"no embed_model anywhere -> off"`
(`doctor_test.go`, was line ~310) configures Ollama unreachable
(`http://127.0.0.1:1`) and Gemini with no `embed_model` — also a
zero-ready-candidate exhaustion, so it necessarily flips to ❌ too under
the same logic, or the fix would be inconsistent (two exhaustion cases,
one ❌ one ⚪, for no principled reason). Renamed to
`"no embed_model anywhere -> broken (zero usable candidates)"` and
updated the assertion.

**Is there a genuinely-intentional ⚪ left for this check?** No — not at
the aggregate `checkEmbedRoute` level. Searched for one and didn't find
it: G2 fails closed unconditionally (even with no priors, per the
existing `TestG2_priorsWithoutEmbedFailsClosed`), so there is no state
where "the whole embed chain is unusable" is actually fine for this
product. The genuinely-intentional ⚪ cases live one level down, at the
*per-provider* checks (`checkOllamaProvider`, `checkOpenAICompatProvider`,
both unchanged) — "Ollama isn't running" or "this one key isn't set" is
still correctly ⚪ there, and also correctly never reaches
`checkEmbedRoute`'s exhaustion branch as long as some other candidate in
the chain resolves (covered by the pre-existing
`"gemini key set, no ollama -> ok, resolves to gemini"` and
`"ollama reachable -> ok, resolves to ollama first"` subtests, both still
passing unmodified). `checkEmbedRoute` itself, as an aggregate "will G2
have a working embedder" check, now only ever returns ok or broken, never
off — which I believe is correct given what the check exists to answer.
