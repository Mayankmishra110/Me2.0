## Goal
`builder.audit` job that reacts to a `subphase.done` event (emitted by M2-502) and, in a second, read-mostly git worktree on the same build branch, reviews the finished subphase's diff against the target repo's `ARCHITECTURE.md`/`DESIGN.md`, writes and runs tests for its acceptance criteria, and (per PRD §6 M6) compares UI to designs with Playwright screenshots where applicable — using `claude -p` (Sonnet 5, `config.builder.auditor_model`). This runs **in parallel** with the Implementer already working on subphase N+1 (D7's core idea — the whole point of the two-thread design). Writes findings to `audit/N.M.md` (`{verdict, findings[]}`, ARCHITECTURE §3.3); findings become fix tasks that M2-504 (phase gate) turns into retries for the Implementer.

## Acceptance criteria
- [ ] `internal/builder/auditor.go` implements the `builder.audit` job: no-op when `config.builder.enabled` is `false`; refuses repos not in `config.builder.repos` (same gate as M2-501/M2-502 — do not name specific repos).
- [ ] Subscribes to / is triggered by the `subphase.done` event from M2-502, and runs in its own worktree (`data/worktrees/<repo>/<branch>-audit` or similar — reuses the same build branch, rebased, per ARCHITECTURE §3.3's "Both rebase on the phase branch before committing").
- [ ] Builds the audit prompt from: the subphase's diff (`git diff` against the subphase's starting commit, fixed argv), the subphase's acceptance criteria (from the plan file M2-501 wrote), and the target repo's `ARCHITECTURE.md`/`DESIGN.md`; runs `claude -p` with `--model` from `config.builder.auditor_model`, honoring `config.builder.run_timeout` as a hard process timeout.
- [ ] Writes/runs tests it authors for gaps it finds, and (when the target repo has a web/UI surface matching a `DESIGN.md` screen) takes Playwright screenshots to compare against the design doc — flagged as best-effort/optional per repo, since not every target repo will have a UI.
- [ ] Writes `audit/N.M.md` in the target repo with a structured verdict (`pass` / `fail`) and a findings list; commits **only** test files and `audit/*.md` — never edits source files the Implementer owns (ARCHITECTURE §3.3: "The Auditor commits only tests and `audit/` files; the Implementer owns source code"). Test asserts the auditor's commit(s) never touch a non-test, non-`audit/` path.
- [ ] **Never pushes to, checks out for commits on, or otherwise modifies the target repo's `main` branch** — same hard, tested guarantee as M2-502 (this job is not exempt just because it's "read-mostly").
- [ ] On `config.builder.run_timeout` exceeded or a detected usage-limit response: returns the same distinguishable result shape as M2-502 so M2-504 can apply its pause logic uniformly across both threads.
- [ ] Table-driven tests next to the file: enabled/disabled gate, repo-not-listed rejection, triggered-by-`subphase.done`, commits-only-tests-and-audit (above), never-touches-main, `audit/N.M.md` written with expected shape, timeout/usage-limit produces the shared distinguishable result.

## Notes
- Same `claude -p` invocation-shape caveat as M2-502 applies here: the Auditor's job (reading a diff, writing/running tests, taking screenshots) is a multi-step coding-agent session, not the single-shot `internal/llm.Complete` pattern M2-111 built for `research`/`script`/`blog`. Confirm the real CLI's flags for this before implementing rather than assuming M2-502's approach transfers unchanged — but do not duplicate that investigation independently; whatever M2-502 settles on for headless multi-turn sessions, timeouts and usage-limit detection should be shared/reused here (same child-process wrapper, ideally), since both jobs need identical mechanics minus the tool allowlist and prompt content.
- Which repos Builder may touch is still open (CONTEXT.md §5, question 1). Everything here is driven by `config.builder.repos` (empty by default) and `config.builder.enabled: false` — don't guess or hardcode a repo name.
- Playwright screenshot comparison assumes the target repo has a web frontend with a `DESIGN.md`; for a target repo without one (e.g. a CLI-only tool), this step should be skipped rather than failing the audit — note this explicitly in the implementation rather than leaving it an unhandled edge case.
