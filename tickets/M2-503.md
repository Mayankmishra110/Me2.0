## Goal
`builder.audit` job that reacts to a `subphase.done` event (emitted by M2-502) and, in a second, read-mostly git worktree on the same build branch, reviews the finished subphase's diff against the target repo's `ARCHITECTURE.md`/`DESIGN.md`, writes and runs tests for its acceptance criteria, and (per PRD §6 M6) compares UI to designs with Playwright screenshots where applicable — using `claude -p` (Sonnet 5, `config.builder.auditor_model`). This runs **in parallel** with the Implementer already working on subphase N+1 (D7's core idea — the whole point of the two-thread design). Writes findings to `audit/N.M.md` (`{verdict, findings[]}`, ARCHITECTURE §3.3); findings become fix tasks that M2-504 (phase gate) turns into retries for the Implementer.

## Notes
- Same `claude -p` invocation-shape caveat as M2-502 applies here: the Auditor's job (reading a diff, writing/running tests, taking screenshots) is a multi-step coding-agent session, not the single-shot `internal/llm.Complete` pattern M2-111 built for `research`/`script`/`blog`. Confirm the real CLI's flags for this before implementing rather than assuming M2-502's approach transfers unchanged — but do not duplicate that investigation independently; whatever M2-502 settles on for headless multi-turn sessions, timeouts and usage-limit detection should be shared/reused here (same child-process wrapper, ideally), since both jobs need identical mechanics minus the tool allowlist and prompt content.
- Which repos Builder may touch is still open (CONTEXT.md §5, question 1). Everything here is driven by `config.builder.repos` (empty by default) and `config.builder.enabled: false` — don't guess or hardcode a repo name.
- Playwright screenshot comparison assumes the target repo has a web frontend with a `DESIGN.md`; for a target repo without one (e.g. a CLI-only tool), this step should be skipped rather than failing the audit — note this explicitly in the implementation rather than leaving it an unhandled edge case.

### Implementation plan (be, 2026-09-28)
1. Branch base: M2-502 (`internal/builder/implementer.go`) is not yet merged into `phase/p1-foundation` (ship hasn't run), so this worktree is based on `m2/M2-502` (tip `72a3d73`), not the phase branch directly — otherwise `auditor.go` can't compile against the shared `builder` package types (`EventEmitter`, `GitRunner`, `ClaudeRunner`, `KindSubphaseDone`, `Outcome*`, `Err*`, `confineUnderRoot`, `truncateRunes`, `phaseNumRe`, `newULID`, `disallowedTools`, `defaultGitRunner`, `defaultClaudeRunner`, `rejectForbiddenGitArgs`). Ship will need to rebase this onto `phase/p1-foundation` once M2-502 lands there — flagging so it isn't missed.
2. New file `internal/builder/auditor.go`, same package (`builder`), reusing every M2-502 primitive above rather than redefining it. New exports: `JobAudit`, `AuditPayload`/`AuditResult`, `AuditorOptions`/`NewAuditor`, `Auditor.Handler()`, `Auditor.Run()`, `Auditor.Subscribe()`, `AuditReport`/`AuditFinding`, `PlaywrightOpts`/`PlaywrightResult`/`PlaywrightRunner`, `EventSubscriber`/`Enqueuer` interfaces.
3. Git worktree design decision (the real ambiguity in this ticket): git refuses to check out a branch already checked out in another worktree, and the Implementer's worktree holds `build/phase-N` for the run's whole duration. So the audit worktree is `git worktree add --detach <path> <branch>` (detached HEAD, no ref conflict), rebased onto the branch tip on every reuse. To land the Auditor's commit back onto the shared branch (required so M2-504's phase gate sees `audit/N.M.md` on the branch it pushes), `fastForwardBranch` does a compare-and-swap `git update-ref refs/heads/<branch> <newSha> <oldTip>` after verifying with `merge-base --is-ancestor` that it's a genuine fast-forward — the same "bypass the checkout-conflict guard with a dedicated fixed-argv ref update" pattern `implementer.go`'s `restoreMainRef` already uses for `main`. A non-fast-forward (Implementer moved the branch in a way this worktree's rebase didn't see) returns a plain retryable error rather than forcing anything.
4. Locating "the subphase's diff": the branch tip is **not** reliable once the Implementer has moved to N+1 (D7), so `findSubphaseCommit` greps commit messages on the branch for `^N.M: ` (matching `implementer.go`'s `commitMsg` format exactly) instead of assuming HEAD.
5. Read-mostly enforcement is a hard gate, not a prompt request: `commitAuditWorktree` reads `git status --porcelain --untracked-files=all` (the `--untracked-files=all` matters — without it a brand-new `audit/` dir collapses into one `?? audit/` line that can never match the per-file allow-list), discards (`checkout --`/`clean -f --`) and refuses to commit (`queue.Permanent`) if anything outside `audit/*.md` or a recognized test-file pattern (`isAuditOrTestPath`: Go/TS/JS/Python conventions) changed.
6. Verdict extraction: the Claude session is asked to end its output with a fenced ```json {"verdict","findings"} block (`buildAuditPrompt`); `parseAuditVerdict` extracts it and **defaults to `fail`** with a synthetic blocker finding if the block is missing or doesn't parse — an audit that can't state its own verdict must never silently read as pass.
7. Risks/things not fully hardened (documented in code comments, not hidden): concurrent non-fast-forward branch moves are surfaced as a retryable error rather than an automatic re-rebase-and-retry loop; whether M2-504 should drive that retry loop is left open below.

### Open question for Mayank (recorded, not guessed on)
- Should a non-fast-forward on landing the Auditor's commit (Implementer advanced the branch in a real conflicting way while the Auditor was working) be retried automatically by re-running the Auditor's rebase, or should M2-504 (phase gate) own that retry loop explicitly? Current behavior: `Run` returns a plain (queue-retryable) error and does nothing further. Recorded in `docs/CONTEXT.md` §5 as well.

1. **Commits only tests + `audit/*.md`, hard-enforced:** traced `commitAuditWorktree` (auditor.go:646-709). It
   runs `git status --porcelain --untracked-files=all` (the `--untracked-files=all` flag is really there —
   without it a fresh `audit/` dir would collapse to one `?? audit/` line that can't match the allow-list),
   classifies every changed path with `isAuditOrTestPath` (auditor.go:738-766), discards (`checkout --` /

   names `src/prod.go`, and both `main` and the build branch are provably unmoved after the refusal. Real.
2. **Never touches `main`, reuses the shared `GitRunner`:** `NewAuditor` defaults `opts.Git =
   defaultGitRunner(opts.LookPath)` (auditor.go:210-212) — the exact same function implementer.go defines
   (implementer.go:748), which calls `rejectForbiddenGitArgs` before every exec. No separate/weaker git path
   exists in auditor.go. Confirmed `fastForwardBranch`'s `update-ref refs/heads/<branch> <sha> <oldTip>` call
   goes through this same `au.opts.Git` (not a raw `exec.Command` bypass like implementer.go's `restoreMainRef`
   uses for `main`) — `rejectForbiddenGitArgs` only blocks `update-ref` when the target is
   `refs/heads/main`/`master`, so a build branch ref update legitimately passes through the real gate rather than
   circumventing it. `TestAuditorNeverTouchesMain` and `TestAuditorWritesAuditFileAndLandsOnBranch` both replay
   every recorded git argv through `rejectForbiddenGitArgs` and assert `main` is byte-identical before/after. Real.
3. **Separate, detached worktree, not the Implementer's:** Implementer's worktree path is
   `DataDir/worktrees/<repo>/<branch>` (implementer.go:277); Auditor's is
   `DataDir/worktrees/<repo>/<branch>-audit` (auditor.go:352) — distinct directories by construction, so there's
   no path collision to even guard against. `ensureAuditWorktree` (auditor.go:515-543) additionally checks the
   worktree's `HEAD` isn't attached to `main`/`master`/`branch` by name (a detached HEAD reports `"HEAD"`, not a
   branch name) and refuses with `queue.Permanent` if it ever finds otherwise — real defense against exactly the
   two-writers collision class called out in the task. Real.
4. **CAS landing (`merge-base --is-ancestor` then `update-ref` old/new), non-FF returns retryable error:**
   `fastForwardBranch` (auditor.go:723-733) checks `merge-base --is-ancestor branchTipBefore sha` first: on
   failure returns a plain wrapped error (not `queue.Permanent`, so the queue retries it) and never calls
   `update-ref`. On success it calls `update-ref refs/heads/<branch> <sha> <branchTipBefore>` — the 3-arg form is
   real optimistic-concurrency compare-and-swap (git refuses if the ref's current value isn't
   `branchTipBefore`). No forcing anywhere in this path. Real, and matches the ticket's own open question
   (recorded, not silently resolved) about who owns the retry loop.
5. **Unparseable verdict defaults to fail, never silently reads as pass:** `parseAuditVerdict`
   (auditor.go:775-808) initializes `report := AuditReport{..., Verdict: VerdictFail}` up front, and only
   overwrites it with `pass` when a fenced JSON block is found AND parses AND its `verdict` field is literally
   `"pass"` — any other case (missing block, bad JSON, unrecognized verdict string) falls through to the
   default-fail with a synthetic blocker finding. `TestParseAuditVerdict` covers all four cases including "no
   block" and "unparseable block", both asserting `VerdictFail` + a non-empty findings list. Real.
6. **Playwright step is genuinely best-effort/bounded, can't hang or fail the audit:** `defaultPlaywrightRunner`
   (auditor.go:874-911) skips cleanly (returns `Skipped: true, nil`) when `DesignPath` is empty or no
   `playwright.config.{ts,js}` is found, and skips (not fails) if `npx` isn't even on `PATH`. When it does run,
   it wraps the run in `context.WithTimeout` (10 min default, bounded — auditor.go:894-899) via
   `exec.CommandContext` with fixed argv, and a non-zero exit is captured as a `Note` string with `nil` error
   (`runErr` is deliberately swallowed at auditor.go:905-907) — it can never propagate up and fail the audit job,
   and it can't hang past its own timeout. `TestAuditorWritesAuditFileAndLandsOnBranch` and
   `TestAuditorCommitsOnlyTestsAndAudit` both inject `Skipped: true` and assert the audit still succeeds end to
   end. Real.
