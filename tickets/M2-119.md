## Goal
`internal/scheduler`'s cron trigger has fired `scout.topics` daily since M2-108/116, but it always hit
`internal/scheduler/handlers.go`'s `placeholderHandler` — a no-op that returns
`{"status":"placeholder","type":"scout.topics"}`. M2-202 (Niche Scout, `status: done`,
`internal/content/scout.go`) built the real topic-discovery service, but nobody swapped the scheduler's
placeholder for it, so the product's core end-to-end loop (SPEC §1 P2 exit check: "Topic → published
YouTube Short") never actually starts on its own — nothing ever seeds the `topics` table automatically.
After this ticket, the daily cron trigger reaches `content.Scout`'s real handler instead.

## Acceptance criteria
- [x] `internal/content/scout.go` gets `JobScoutTopics = "scout.topics"`, `Scout.RegisterHandler(q)` (net
      resource class — YouTube Data API / RSS / Trends are HTTP calls, not a local model load or a render,
      so CLAUDE.md's "heavy" rule doesn't apply), and a `handleJob` that: loads `config/channels/*.yaml`
      fresh via `LoadChannels` (`ScoutOptions.ChannelsDir`, new field), syncs them into the `channels` table
      via `SyncChannels` (M2-201 — `Scout.Run`'s own doc comment requires the channel already exist there,
      FK; nothing else in `cmd/mayank2` calls `SyncChannels` outside tests, a real pre-existing gap this
      ticket had to close to invoke `Run` correctly, not new chaining behavior), then calls `Scout.Run`
      once per channel with that channel's `warmup_started_at` (so the week-4+ analytics blend in `Run`
      actually activates when eligible). Per-channel failures are collected and reported in the result
      (`channels`/`topics_written`/`errors`) rather than failing the whole job on one bad channel; the job
      only errors (retryable) when every channel failed.
- [x] `internal/scheduler/handlers.go`'s `RegisterHandlers` no longer registers a placeholder for
      `scout.topics` (same pattern M2-116 used to drop the `analytics.pull` placeholder) — the unused
      `placeholderHandler` helper is removed since nothing calls it anymore.
- [x] `cmd/mayank2/run.go` builds `content.Scout` via `NewScoutFromEnv` (`YOUTUBE_API_KEY`, CONTEXT D24)
      and registers its real handler. Unlike `blog.*` (which skips registration entirely when
      unconfigured), `scout.topics` is **always** registered even when `*ScoutNotConfiguredError`: the
      scheduler's cron trigger enqueues it unconditionally every day, so leaving the type unregistered
      would turn into a genuine `"job type not registered"` error every day instead of a clean, expected
      skip. The unconfigured branch registers a small inline handler that logs and returns
      `{"status":"skipped","reason":"not configured"}` — success, not error, so the queue's retry/failure
      accounting doesn't flag a daily "failure" for a key Mayank hasn't added yet.
- [x] No new required config: `YOUTUBE_API_KEY` was already the documented D24 key for this service (scout.go,
      pre-existing); `RSSFeeds`/`TrendsBaseURL` remain unexposed via `config.yaml` (no config field existed
      before this ticket and none was added — out of scope, flagged below) so YouTube is the only signal
      source reachable from the running daemon today.
- [x] `cmd/mayank2/run_test.go` gets `TestRunDaemon_scoutTopicsIsRealHandler`, proving (network-free) that
      the scheduler's old fixed placeholder shape is gone: (1) unconfigured → the distinct
      `status=skipped/reason="not configured"` shape, not `{"status":"placeholder",...}`; (2) configured
      (`YOUTUBE_API_KEY` set) with an empty `ChannelsDir` → the real handler's own
      `channels`/`topics_written`/`errors` result shape, with zero counts since `LoadChannels` found no
      `*.yaml` and made no outbound HTTP call.
- [x] Real check output pasted below (gofmt / go vet / go test ./... -count=1).

**Investigation findings (per the ticket brief's step 1/2/3):**
- `internal/content/scout.go` had **no** `RegisterHandler` before this ticket (unlike `research.go`/
  `script.go`, M2-117's pattern) — added one, following the exact same method shape
  (`RegisterHandler(q *queue.Queue)`, nil-receiver/nil-queue guard).
- The scheduler's placeholder (`internal/scheduler/handlers.go`, pre-edit) was a literal no-op returning
  `{"status":"placeholder","type":jobType}` — confirmed by reading it before removing it.
- The scheduler's cron trigger enqueues `scout.topics` with payload `{"trigger":"cron"}`
  (`scheduler.go` `enqueueTrigger`) — no channel info. `Scout.Run` takes a `Channel` argument and writes
  directly to the `topics` table (`insertTopic`, status `new`) — it does **not** enqueue `research.brief`
  or anything else. Confirmed against `docs/ARCHITECTURE.md` §3's own diagram
  (`scheduler (daily per channel) ─► scout.topics ─► topics table (scored)`, and separately
  `Mayank input ─► topics table (source=manual, priority boost)` for `AddManual`/the dashboard/Telegram
  path) — topic → research.brief is a **separate**, not-yet-existing hop (picking a topic and starting
  research), out of this ticket's scope; not invented here.
- A real, separate gap found while wiring this: `content.SyncChannels` (M2-201) was never called from
  `cmd/mayank2` in production code — only from its own package's tests. Since `Scout.Run`'s doc comment
  states the channel row must already exist in `channels` (FK), the daily cron job would have failed with
  an FK violation the first time it ran for real, even with the real handler wired, if this weren't closed
  too. Fixed inside `handleJob` itself (load + sync channels on every fire) rather than adding new
  standalone wiring elsewhere in `run.go`, keeping the fix scoped to what this handler needs to function.

**M2-118 collision check** (per the ticket brief's step 4): fetched `origin/main` fresh
(`0c89460`) before branching; `cmd/mayank2/run.go` on that commit already carries the httpapi bind/serve
wiring — no separate M2-118 branch/PR was open against this repo at the time this worktree was created, so
there was nothing to rebase onto. If a concurrent M2-118 branch reaches `origin/main` with different
`run.go` edits before this merges, a rebase here is expected, per the brief.

### Open question / follow-up not addressed here

`YOUTUBE_API_KEY` is the only signal source the running daemon can use today. Flagged as a CONTEXT.md
