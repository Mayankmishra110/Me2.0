## Goal
`registerPublishHandlers` (`cmd/mayank2/run.go`) never assigned Instagram/Facebook/Pinterest's `Presign`
field — it was left at its nil zero value, and nothing else in the repo ever built a real
`*storage.R2Client` to wire in either. Every real publish attempt to those three platforms was
therefore guaranteed to fail (`R2 presigner not configured`) even with valid `R2_*` credentials
present in `.env` — a crash-adjacent, product-breaking gap in code M2-116 and QA both signed off as
"genuinely done". This ticket wires a real presigner in, and degrades cleanly (never panics) when R2
isn't configured, per CONTEXT D24.

## Audit correction (read before assuming the original report)
The bug that prompted this ticket was originally described as a **nil-interface panic**: "`Publish()`
unconditionally calls `i.Presign.PresignGET(...)`... the first real publish attempt... would panic on
a nil interface method call." That specific claim is **false** — verified by reading all three call
sites:
- `internal/publish/instagram.go` `resolvePublicURL` (line 171): `if i.Presign == nil { return "",
  fmt.Errorf("publish/instagram: R2 presigner not configured") }` before ever touching `i.Presign`.
- `internal/publish/facebook.go` `resolvePublicURL` (line 182): identical `if f.Presign == nil`
  guard.
- `internal/publish/pinterest.go` `resolveCoverURL` (line 209): identical `if p.Presign == nil`
  guard.

All three already null-check `Presign` before calling `PresignGET` and return a clean error. So a nil
`Presign` was **never** a panic risk — `internal/publish/presign_notconfigured_test.go`'s
`TestInstagram_NilPresign_ReturnsCleanError` proves this directly (nil Presign, no recover needed,
clean error).

**The real bug** is narrower but still real: `registerPublishHandlers` never built a `*storage.R2Client`
or assigned it to `Presign` *at all*, regardless of whether `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/
`R2_SECRET_ACCESS_KEY`/`R2_BUCKET` were actually set in `.env`. So even a fully-configured R2 bucket
could never be used — every Instagram/Facebook/Pinterest publish would fail with "R2 presigner not
configured" forever, which is a permanent functional break dressed up as a "not configured yet"
message. That's the bug this ticket fixes.

`publish.YouTube` and `publish.X` have no `Presign` field at all and need none — both upload the local
file directly (`internal/publish/youtube.go` `confine()`+`openFile()`+resumable upload,
`internal/publish/x.go` `confine()`+chunked media upload), per M2-211's own documented flow. Out of
scope, confirmed by reading both files.

## Fix
`cmd/mayank2/run.go` `registerPublishHandlers`:
- `buildPresigner(log)` builds one real `*storage.R2Client` via `storage.NewR2FromEnv(nil,
  storage.R2Options{})` — the same construction `internal/scheduler/cleanup.go`'s
  `handleStorageCleanup` already uses for `storage.cleanup`'s optional R2 delete (grep-confirmed:
  that's the *only* other place in the repo that calls `storage.NewR2FromEnv`).
- When R2 **is** configured, the real `*storage.R2Client` is wired directly into `Instagram.Presign`,
  `Facebook.Presign`, `Pinterest.Presign` (all three take the same unexported single-method interface
  shape — `PresignGET(ctx, key, expiry) (url, ttl, err)` — so one concrete value satisfies all three
  structurally).
- When R2 **is not** configured (`*storage.NotConfiguredError`, CONTEXT D24), `buildPresigner` returns
  `notConfiguredPresigner{err}` instead of nil: a real, non-nil `PresignGET` that returns a clean,
  typed `"publish: r2 presign: r2 not configured: set ..."` error the moment a publish job actually
  needs a presigned URL. This is defense in depth on top of each publisher's own nil guard (see audit
  correction above) — not required for panic-safety (the guards already did that), but it gives a
  single consistent error message and removes the reliance on three separate copies of the same nil
  check.
- `R2KeyResolver` (Facebook/Instagram/Pinterest) is left nil, unchanged — see **Open question** below.

## Open question — R2KeyResolver's nil-fallback assumption does not hold
M2-116's Notes claimed: "all three publishers... treat `nil` as 'use the local `VideoPath` directly'
per their own doc comments, so this is a safe default, not a broken one." That's true only in the
narrow sense that the *field* correctly falls back to `VideoPath` as the R2 *key* name. It does **not**
mean the fallback is *correct end-to-end*: presigning a GET for `VideoPath` only works if something
actually uploaded the render to R2 under that exact key first.

Checked: **nothing in this repo ever calls `(*storage.R2Client).Upload` in production code.**
```
$ git grep -n "\.Upload(ctx" -- internal cmd
internal/storage/r2_test.go:147:	if err := r2.Upload(ctx, ...
```
That's the only hit — a test file. `internal/content/render.go` (`Renderer.renderVideo` et al.) writes
finished MP4s only to the local `storage.KindRenders` directory (`filepath.Join(outDir, outName)`); no
render or publish code path uploads that file to R2 under any key.

So even after this ticket's fix, with real R2 credentials configured, a presigned GET for
`p.VideoPath` (e.g. `renders/<content_id>/short.mp4`) will point at an object that was never
uploaded — Meta/Pinterest's fetch of that URL will 404. **This is a real, separate gap, not fixed by
this ticket** (crash-prevention/wiring scope only, per this ticket's brief) — it needs a decision on
where in the render pipeline an R2 upload belongs (render-time? a dedicated `publish.prepare` step?)
and is out of `touches: [cmd/mayank2/run.go, internal/publish/]`. Flagging here per CLAUDE.md ("write
the question under Open questions in CONTEXT.md instead of guessing") — added as CONTEXT.md §5 Open
question (see Notes).
