## Goal
Take the approved, now-live Mayankbuilt post and produce a LinkedIn-native repost — shorter, its own hook, not a raw copy-paste — then publish it via LinkedIn's official Posts API once Mayank approves it (D5).

## Acceptance criteria
- [x] `internal/blog/repurpose_linkedin.go` implements the LinkedIn leg of `blog.repurpose`: input is the live Mayankbuilt post (URL + body, from M2-401's `publications` row); calls `internal/llm.Complete(ctx, "blog", req)` (still the `blog` task/Claude route — this is rewriting the same post, not a content-engine task) to produce a LinkedIn-native draft: shorter, its own hook, and a link back to the canonical post.
  Proved by: `Repurposer.Run` → `complete` calls `Completer.Complete(ctx, llm.TaskBlog, ...)` (`repurpose_linkedin.go:235`); `LoadSourcePost` reads URL from `publications` (platform="mayankbuilt") and body from the `mdx` asset — see Notes for the exact interpretation, since `publications` itself has no body column. `TestLoadSourcePost`, `TestRepurposer_Run_HappyPath` pass.
- [x] Output is not a raw copy-paste of the blog post — a test asserts the LinkedIn draft text is substantially different from (shorter than, different opening line than) the source MDX body.
  Proved by: `validateDraft` checks word count, opening line, and an 8+/12-word shared-run bound (COMPLIANCE G1's own threshold, reused as the bar here). `TestValidateDraft`, `TestRepurposer_Run_NotCopyPaste` (a literal source truncation is rejected and retried), `TestRepurposer_Run_AlwaysCopyPaste_PermanentError` (dead-letters via `queue.Permanent`/`ErrDraftNotOriginal` instead of looping forever) all pass.
- [x] Creates an `approval.request` (`content_items.kind = "blog"`, platform `"linkedin"`) with the draft text and source link; Reject/Redo(note) re-runs the repurpose step with the note, same pattern as M2-401.
  Proved by: `Repurposer.Run` calls `Approver.Start(ctx, contentID, "linkedin", summary, "")` with a summary containing the full draft text + source URL (`TestRepurposer_Run_HappyPath` asserts both are present). `RunInput.RedoNotes` is threaded into the prompt (`TestRepurposer_Run_RedoNotesInPrompt`). See Notes on the redo **wiring** gap this surfaces upstream.
- [x] `internal/publish/linkedin.go` implements `Publisher`: `Platform()` returns `"linkedin"`; `Publish(ctx, PublishRequest)` is idempotent on `p.IdempotencyKey` (checks `publications.idempotency_key` before calling the API).
  Proved by: `TestLinkedIn_Idempotent` (second call makes 0 API calls, returns the stored identity).
- [x] Refuses to call the API unless the item's `approvals` row is `status = approved` (D5, F7) — same `RequireApproved` helper pattern as M2-301/302/303/304.
  Proved by: `TestLinkedIn_RequiresApproval`.
- [x] Publishes via LinkedIn's official Posts API under Mayank's personal LinkedIn member URN, using an access token read from `internal/secrets` (DPAPI vault) by account ref — never `.env` plaintext, never logged.
  Proved by: `LinkedIn.Tokens TokenSourceFor` (same shape as `publish.YouTube`/`publish.Instagram`, backed by `secrets.Store.TokenSource` in production, `staticToken` in tests) — no `.env` read anywhere in `linkedin.go`. Author URN comes from `WhoAmI` (OIDC `/v2/userinfo`), not a config value. `liRedact` strips bearer/access_token/oauth-shaped substrings before anything reaches `last_error` or logs; `TestLinkedIn_CreatePostAPIError` and `TestLiRedact` assert no token substring survives.
- [x] Respects the LinkedIn daily cap (≤ 1 post/day, COMPLIANCE §4) — fails closed rather than queuing past it.
  Proved by: `reserveCap` (same `quotas` table + `ON CONFLICT ... WHERE` guard pattern as `publish.Instagram.reserveCap`), cap = `linkedInDailyCap = 1`. `TestLinkedIn_DailyCapExceeded`.
- [x] On success, records `external_id` and post `url` in `publications`; on failure, wraps the API error with `%w`, error detail (not the token) in `last_error`.
  Proved by: `TestLinkedIn_PublishHappyPath` (checks `publications.status/external_id`), `TestLinkedIn_CreatePostAPIError` (checks `last_error` has no token substring), `fmt.Errorf(...: %w, err)` wrapping throughout `Publish`.
- [x] Table-driven tests cover: repurposed text differs from source, idempotent replay, missing approval, cap exceeded, happy-path publish against a fake LinkedIn API server (`httptest`).
  `internal/publish/linkedin_test.go`: happy path, idempotent, missing approval, cap exceeded, empty text, API error (+redaction), queue `Handle` (success + permanent-on-not-approved), `HTTPLinkedInAPI` against `httptest` (`WhoAmI`, `CreatePost` incl. header assertions and both id-in-header/id-in-body paths), and a full `LinkedIn.Publish` run through the real HTTP client against an `httptest` server. `internal/blog/repurpose_linkedin_test.go`: originality/validation table, retry-then-succeed, always-fails→permanent error, redo notes, missing source fields, `LoadSourcePost` against a real (temp) sqlite DB + temp MDX file.

## Notes
- **Plan** (per _engineer.md): read the M2-211 (`youtube.go`) and M2-301 (`instagram.go`, on its own in-progress worktree) `Publisher` shapes and reused their exact pattern for `linkedin.go` (idempotency lookup → daily-cap reserve → mark publishing → token → API call → complete/fail publication), since Instagram's `reserveCap`/`quotas` pattern is the closer analog (a capped social post, not a quota-*unit* video upload like YouTube). For `repurpose_linkedin.go`, followed `internal/content/script.go`'s `Completer` + retry-on-validation-failure shape, and `internal/content/approval.go`'s `ApprovalService.Start` for the approval-gate call (abstracted behind a local `Approver` interface so this package's tests don't need a full DB/queue wire-up). Risk found and fixed during implementation: a copy-pasted `redact()`-style helper (`liRedact`) had an infinite loop (the needle was never consumed, so the search kept re-matching the same position forever once the string stabilized at "[redacted]") — confirmed live via a pegged-CPU `go test` process, fixed with a monotonically-advancing search offset, and covered by a dedicated `TestLiRedact` with a 5s deadline so a regression fails fast instead of hanging a worker. Worth flagging: `internal/publish/instagram.go`'s `igRedact` (M2-301, not touched here) appears to share the same pattern — a real reliability risk for whoever owns that file, since an in-process infinite loop has no timeout protection the way child processes do (CLAUDE.md's timeout rule only covers `exec.Command`).
- **LinkedIn API shape — NOT VERIFIED against live docs (this ticket's flagged uncertainty), best-guess implementation, isolated behind `LinkedInAPI`/`HTTPLinkedInAPI` so it's a one-file change if wrong:**
  - Implemented the newer **Posts API** (`POST /rest/posts`, `LinkedIn-Version` + `X-Restli-Protocol-Version: 2.0.0` headers), not the legacy `/v2/ugcPosts`, as the best-guess current endpoint. `linkedInAPIVersion = "202401"` is a placeholder and will be stale by the time this runs for real.
  - Scopes unchanged from `secrets/platform.go` (`openid profile w_member_social`) — `w_member_social` needs Marketing Developer Platform / "Share on LinkedIn" product approval; app-review tier not verified.
  - Author URN is resolved via the standard OIDC `GET /v2/userinfo` (`sub` → `urn:li:person:{sub}`) rather than a LinkedIn-specific guess — most stable piece of this file since it follows the OIDC spec, not LinkedIn's product surface.
  - Response id: checks the `x-restli-id` response header first, falls back to a body `id` field — not confirmed which one the live API actually uses.
  - `PublishResult.URL` is built from the `https://www.linkedin.com/feed/update/{urn}/` pattern (LinkedIn's common share-permalink shape) — there's no documented permalink field on create; not confirmed for every visibility/post-type combination.
  - **QA/SEC: please check all five of the above against current LinkedIn API docs before this ever runs against a real app** (same ask as M2-302's Meta-endpoint flags — see `crew/state/be-2.md`).
- CONTENT_STRATEGY §4's craft rules are written for video scripts (hook in first 2 seconds, loopable last line, chapters, etc.), not LinkedIn text posts. Adapted the underlying principle — a real, specific hook rather than a teaser dump of the article — into the `linkedInSystemPrompt` in `repurpose_linkedin.go`; there is no LinkedIn-specific craft section anywhere in the docs, so these exact style rules are this ticket's own interpretation, not spec — worth checking against real LinkedIn post examples.
- Docs don't say whether there's more than one LinkedIn account in scope; assumed a single Mayank-personal LinkedIn account per CONTEXT D12.
- **M2-401 is not built yet** (this ticket depends on it, but its worktree has no `internal/blog/*.go` as of this session — only ticket claim commits). Two decisions had to be made without it, documented in code comments and flagged here for whoever lands M2-401 / reviews this:
  1. `publications` (`migrations/001_init.sql`) has no body/content column. `LoadSourcePost` reads the canonical URL from `publications` (platform="mayankbuilt", status="published") but reads the post **body** from the content item's `assets` row of `kind="mdx"` (reads the file at `assets.path`, strips MDX frontmatter). If M2-401 stores the body some other way, only `LoadSourcePost` needs to change — `Repurposer.Run` only depends on the `SourcePost{ContentID, URL, Body}` struct, not on how it was loaded.
  2. The repurpose approval **reuses the same `content_id`** as the original blog post/merge approval, with `approvals.kind = "linkedin"` (that column has no CHECK constraint) to distinguish it. Checked this is safe against `RequireApproved`'s `ORDER BY decided_at DESC LIMIT 1` (`internal/content/approval.go`): by construction this leg only runs after the post is live, i.e. after the original approval was already decided, so the repurpose approval's `decided_at` is always the later one once it too is decided — no cross-contamination between the two approval decisions for the same content item.
  3. **Gap for a follow-up ticket, not fixable here** (`internal/content/approval.go` is outside this ticket's `touches`): `ApprovalService.Decide` currently hardcodes `content.JobScriptWrite` as the redo-enqueue job for *every* redo decision, regardless of content kind. For a `kind="linkedin"` redo to actually re-run `Repurposer.Run` with the note (as this ticket's AC3 describes), `Decide` (or its caller) needs to route the redo job by content kind / approval kind instead of always enqueuing `script.write`. Flagging this explicitly rather than guessing at product behavior for how that routing should work.
- Also for the ship/integration step that wires the approval **decision** (not in this ticket's touches): `ApprovalService.Decide`'s default `DestinationsFor(channelID, kind, language)` only special-cases `"long"` vs. everything-else (which returns the *video* fan-out: YouTube+IG+FB+X+Pinterest). Approving the LinkedIn repurpose approval must pass an explicit `Destinations: [{Platform: "linkedin", Account: <account>}]` override, or it will try to schedule the wrong publications.
