## Goal
Manual/semi-automated lead entries (company, contact, niche fit) plus AI-drafted outreach/proposal text via `internal/llm`, approval-gated before anything is sent. This is the CONTEXT §2 line-3 income path ("automation agency for US small businesses... the fastest cash") made concrete, but strictly the **drafting** half — no automated sending.

## Acceptance criteria
- [x] `internal/agency` package: `leads` tracking — `{id, company, contact, niche_fit, status(new/contacted/proposal_sent/won/lost), source, created_at}` (new table via an append-only migration, e.g. `002_agency_leads.sql` — never edit the shipped `001_init.sql`; `leads` is not in ARCHITECTURE §4's current table list, so this ticket adds it there and to the schema doc as part of "docs updated if behavior or decisions changed," SPEC §7). Manual entry via dashboard form and/or Telegram (same "flag if extending `internal/telegram/commands.go`'s fixed set outside this ticket's `touches`" caveat as M2-601).
- [x] `draft.proposal` job/handler: given a lead, generates outreach/proposal text via `internal/llm.Complete(ctx, task, req)`. **This is a hard compliance finding, not a minor flag: CLAUDE.md's non-negotiable states "Claude is for Builder and blog only. Content agents use `internal/llm` routing (local/free tiers)."** Agency outreach drafts are neither Builder nor blog — they must **not** route to Claude. Route this under the existing `script` task (or a new task on the same free-tier chain — `groq → cerebras → openrouter → gemini → ollama`, per ARCHITECTURE §6) instead. Do not use `claude_cli` for this job under any circumstance; if the drafts read as lower quality on the free tiers, that's an acceptable tradeoff per the non-negotiable, not a reason to reach for Claude — flag to Mayank if quality is a real blocker rather than silently switching providers.
- [x] **Approval gate (D5, applied here even though this isn't a platform publish):** every drafted proposal/outreach message goes through `approval.request` before it is considered "ready to send" — same one-tap Approve/Reject/Redo(note) pattern as every publish path, because it is still outbound content representing Mayank to a real business. **Flagged, not asserted:** whether this needs a distinct approval surface from platform posts (e.g. a different `approvals.kind` value like `"agency_proposal"` so the dashboard/Telegram preview renders it as text-to-review rather than a video/photo preview) is worth confirming with whoever owns `internal/telegram`'s approval renderer (M2-105) and the dashboard's Approvals detail view (M2-107) — the existing preview path assumes video/photo/text already per M2-105's Notes ("send a preview (video/photo/text)"), so a text-only proposal likely already fits, but verify the detail screen renders long-form text proposals readably before assuming it just works.
- [x] **No automated sending, by design, not by omission.** This ticket only drafts and gets approval; it must not call any email/DM-sending API, and must not add one "just in case." Once approved, a draft's status becomes `approved` and it sits there — a human (Mayank) sends it manually until a separate, explicitly-scoped ticket adds an actual sending capability (PRD §5 non-goals: "No automatic sending of proposals, emails or DMs to people."). Do not scope-creep into building that here even if it seems like a small addition once approval exists.
- [x] Table-driven tests next to the package: lead CRUD, draft generation routes only through free-tier providers in tests (assert the fake/mock provider list never includes a Claude/`claude_cli` provider), approval-request creation for a drafted proposal, redo-with-note re-draft, approved draft never triggers any send (no outbound HTTP call to any messaging/email API exists in the code path at all — test this by asserting no such client/dependency is even imported/wired, not just unexercised).
