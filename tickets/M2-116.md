## Goal
`mayank2 run` stops being a stub (`cmdStub` prints "not implemented yet") and becomes the one place that
starts the whole daemon described in ARCHITECTURE §1: opens the DB, recovers abandoned job leases, sizes
and starts the queue's worker pools, registers every job handler exactly once, starts the scheduler's cron
triggers, starts the Telegram long-poll loop, and starts the HTTP/SSE server — all under one cancellable
context so the process is the single thing Task Scheduler supervises (ARCHITECTURE §8) and Ctrl+C / service
stop shuts everything down without abandoning in-flight work. This is the ticket that makes SPEC §1's P1
exit check runnable at all: "a test job flows queue → Telegram approval → dashboard."

Audit finding this closes: no ticket currently wires `run`; `internal/queue`, `internal/events`,
`internal/scheduler`, `internal/telegram`, `internal/httpapi`, `internal/content`, `internal/compliance`,
`internal/publish`, `internal/analytics`, `internal/storage` are each built and unit-tested in isolation on
`phase/p1-foundation` but nothing calls their `RegisterHandlers`/`Run`/`Start`/`ListenAndServe` together.

**Deliberately left unwired** (no ticket has built a real handler for these yet, confirmed by grep — no
`RegisterHandler(s)` method exists in any of these packages): `research.brief`, `script.write`,
`visuals.fetch`, `blog.draft`, `blog.merge`, `blog.repurpose`. Per this session's task brief:
`content.ApprovalService`'s `blog.draft`-shaped work has no `config.Config.Blog` section to construct
from — flagged below as a CONTEXT.md §5 gap for a future ticket.

**`scout.topics` deviation from the task brief's research pass:** that research said to leave `scout.topics`
entirely unregistered (no real handler exists). I kept it wired to `scheduler`'s existing placeholder
instead, because `internal/scheduler/scheduler.go`'s own cron trigger list already fires `scout.topics`
daily at 06:00 regardless of this ticket (`scoutTr` in `New()`) — if nothing is registered for that type,
every cron-fired `scout.topics` job would sit `queued` forever with no worker able to claim/finalize it
(worse than a harmless placeholder result). Since `internal/scheduler/scheduler.go`'s trigger list is
outside this ticket's `touches`, the safer fix inside `cmd/mayank2/` was to keep calling
`scheduler.RegisterHandlers()` as a whole (which still includes the `scout.topics` placeholder) rather than
leaving a cron-fired job type completely unhandled. This matches the ticket's own original acceptance
table ("wire the placeholder, swap when M2-202 lands") — flagging the discrepancy with the task brief's
research explicitly here rather than silently picking one.

**`builder.implement`/`builder.audit` resource-class judgment call:** neither ARCHITECTURE nor SPEC assigns
resource classes to the four builder job types. I used `queue.ResourceNet` for `implement`/`audit` (not
`ResourceHeavy`): CONTEXT D7 requires the Implementer and Auditor threads to run *in parallel*
(Implementer on subphase N while Auditor audits N-1), which needs 2 concurrent workers for those two job
types; `ResourceHeavy` is capped at 1 worker by design (16 GB RAM / one local-model-or-render job at a
time — CLAUDE.md's "heavy" rule is specifically about things that render or load a local model, which
`claude -p` does not: it's a network call to the Claude API), while `ResourceNet`'s default `net_workers: 2`
(`config/config.example.yaml`) matches the "exactly 2 parallel builder threads" requirement exactly.
`builder.plan`/`builder.gate` are quick single-shot decisions, so `ResourceLight`. Flagging this as a
judgment call for QA/SEC to confirm rather than a documented decision.

**R2 (`storage.R2Client`) not wired into publish handlers' `R2KeyResolver`:** all three publishers that
have an `R2KeyResolver` field (`Facebook`, `Instagram`; `Pinterest` — not fully re-checked) treat `nil` as
"use the local `VideoPath` directly" per their own doc comments, so this is a safe default, not a broken
one. Building a real `R2Client` and wiring key resolution is genuine additional product logic (which local
path maps to which R2 object key, presign lifetime, cleanup) that isn't described anywhere in this ticket's
acceptance criteria (only "register every real handler exactly once"), so I left it as the documented
default and did not invent that behavior. Flag for a follow-up ticket if Mayank wants R2 actually used at
publish time (D20 implies it should be, for Instagram/Facebook's public-URL requirement specifically).

**OAuth token wiring:** every publish/analytics handler's `Tokens` field is a lazy closure
(`tokenSourceFor` in `run.go`) that only calls `secrets.LookupPlatform`/`OAuthConfig`/`Store.TokenSource`
when a job actually runs — so a missing `*_CLIENT_ID`/`*_CLIENT_SECRET` env pair fails that one publish job
cleanly at run time instead of blocking daemon startup (CONTEXT D24). `OAUTH_REDIRECT_PORT` env var
(default `8912`) controls the loopback redirect URL, matching `cmd/mayank2/auth.go`'s own flow.

**`DASHBOARD_TOKEN` treated as required (fatal if unset), unlike Telegram:** `internal/telegram` has an
explicit `ErrDisabled` contract making it an optional, cleanly-off integration; `internal/httpapi.New`
has no equivalent contract — it hard-errors if `DashboardToken` is empty. The dashboard/HTTP server is
listed in ARCHITECTURE §1 as one of the always-on core components (not listed under §6's "external
accounts Mayank must set up gradually"), so `run` fails startup (non-zero exit, ARCHITECTURE §8) if
`DASHBOARD_TOKEN` is missing rather than silently starting without a dashboard. Flag for Mayank/CONTEXT if
this should instead be a soft-off feature like Telegram.

**`queue.Queue.Register`'s new duplicate guard + `internal/scheduler/handlers.go`'s fix required touching
outside `cmd/mayank2/`:** both changes are explicitly called for by this ticket's own acceptance criteria
text (which predates and overrides the `touches: [cmd/mayank2/]` header for just these two files) — noted
here for the record since a literal reading of `touches` would exclude them. `internal/scheduler/handlers.go`'s
`RegisterHandlers` no longer registering `analytics.pull` also required updating
`internal/scheduler/scheduler_test.go` (added `registerFakeAnalyticsPull` helper, called in the two tests
that exercise `Start()`/catch-up for that trigger) so the scheduler package's own tests keep passing without
depending on `cmd/mayank2`.
