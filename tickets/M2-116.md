## Goal
`mayank2 run` stops being a stub (`cmdStub` prints "not implemented yet") and becomes the one place that
starts the whole daemon described in ARCHITECTURE §1: opens the DB, recovers abandoned job leases, sizes
and starts the queue's worker pools, registers every job handler exactly once, starts the scheduler's cron
triggers, starts the Telegram long-poll loop, and starts the HTTP/SSE server — all under one cancellable
context so the process is the single thing Task Scheduler supervises (ARCHITECTURE §8) and Ctrl+C / service
stop shuts everything down without abandoning in-flight work. This is the ticket that makes SPEC §1's P1
exit check runnable at all: "a test job flows queue → Telegram approval → dashboard."

Audit finding this closes: no ticket currently wires `run`; `internal/queue`, `internal/events`,
`internal/scheduler`, `internal/telegram`, `internal/httpapi`, `internal/content`, `internal/compliance`,
`internal/publish`, `internal/analytics`, `internal/storage` are each built and unit-tested in isolation on
`phase/p1-foundation` but nothing calls their `RegisterHandlers`/`Run`/`Start`/`ListenAndServe` together.

## Acceptance criteria
- [ ] `cmd/mayank2/run.go` (new file) implements `cmdRun`, wired from `main.go`'s `case "run"` in place of
      `cmdStub("run", rest)`. Reuses `defaultPaths()` / config-loading conventions already used by
      `cmdDoctor`/`cmdMigrate` (same `-config`/`-env` flags).
- [ ] Startup order, in one function, before anything else can touch the queue:
      1. Load config + `.env`.
      2. `internal/db.Open` + run embedded migrations (same call `cmdMigrate` uses).
      3. Construct `queue.New(db, ...)`.
      4. `queue.RecoverExpiredLeases(ctx)` — call and log the count **before** `StartWorkers` (per its own
         doc comment: "Call this once at startup... before StartWorkers").
      5. Register every job handler exactly once (see ownership table below), from this one function —
         no other init path may also call `.Register` for the same type.
      6. `queue.StartWorkers(ctx, cfg)` — size `HeavyWorkers`/`LightWorkers`/`NetWorkers` from
         config's queue section (`heavy_workers`/`light_workers`/`net_workers`), not hardcoded.
      7. `scheduler.Start(ctx)` (cron triggers only enqueue, per M2-108 — no inline work).
      8. `telegram.Bot.Run(ctx)` (long-poll loop).
      9. `httpapi.Server.ListenAndServe(ctx, listen)` (binds loopback + Tailscale IP per ARCHITECTURE §7).
      All of 7–9 run as goroutines under one `context.Context` derived from `signal.NotifyContext`
      (SIGINT/SIGTERM) so Ctrl+C / Windows service stop cancels everything at once.
- [ ] **Job handler registration — single point, no duplicates.** `cmdRun` (or a small `internal`-only

- [ ] `queue.Queue.Register` (`internal/queue/queue.go`) gets a duplicate-registration guard: calling it
      twice for the same `jobType` returns an error (or panics with a clear message, matching its existing
      style of panicking on other programmer-error inputs like empty `jobType`/invalid `Resource`) instead
      of silently overwriting the map entry. Add a table-driven test proving: (a) registering the same
      `jobType` twice fails loudly, (b) registering two different types still both work.
- [ ] Graceful shutdown test: start a `Queue` with a real (short-`LeaseTTL`) handler that blocks mid-write
      until signalled, enqueue a job, let a worker claim it, cancel the run context, and assert the job is
      not left `dead`/abandoned — it either finishes and is recorded `succeeded`, or its lease is left
      valid for `RecoverExpiredLeases` to reclaim on the next start (i.e., shutdown does not mark
      in-flight work `failed`/`dead` out from under it).
- [ ] `mayank2 run` logs each subsystem's startup (db opened, leases recovered: N, workers started:
      heavy/light/net counts, scheduler started, telegram bot started, http listening on <addrs>) via
      `log/slog`, and logs a clean shutdown line when the context is cancelled.
- [ ] SPEC §1 P1 exit check run once built and pasted into this ticket's Notes: `mayank2 doctor` all green,
      and a manual/scripted test job flowing queue → Telegram approval → dashboard (e.g. enqueue
      `approval.request` for a fake content item, approve it from Telegram, see it reflected on the
      dashboard via SSE).

`depends` lists every P1 ticket whose component this ticket starts, checked against `main`'s actual ticket

token reads at publish time), M2-111 (llm router) were all `status: done`. (M2-101 skeleton/config and
M2-102 db are also `done` and implicitly needed, but are transitive dependencies of the above rather than
listed again per the audit's naming of the "M2-103/104/105/106/108/110/111" set.)

Important: the actual package code for all of this lives on branch `phase/p1-foundation`, not on `main`
yet (per D25, each feature merges to `main` via its own PR; `main` currently only carries ticket docs,
`config/`, and `internal/tickets`). This ticket's implementer works from a worktree/branch based on
`phase/p1-foundation` (or whatever `main` looks like once earlier PRs land) so `cmd/mayank2/run.go` can
actually import and call the real `RegisterHandlers` functions listed above — verify current package
locations again at claim time in case merges have happened since this was written.

Open question for CONTEXT.md if still unresolved at claim time: should `scheduler.RegisterHandlers` be
changed to stop registering an `analytics.pull` placeholder at all (cleanest — scheduler never owned the
real handler), or should it keep a fallback placeholder used only when `internal/analytics` isn't wired
(e.g. for a `run` mode that skips YouTube)? This ticket assumes the former (remove the placeholder for
`analytics.pull` from scheduler once `internal/analytics`'s real handler is always wired in `cmdRun`) since
`run` always wires analytics per this ticket's acceptance criteria — flag in CONTEXT.md §Open questions if
the implementer finds a reason `run` might start without analytics.
