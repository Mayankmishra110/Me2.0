## Goal
Takes a product idea (manual input from Mayank — dashboard form or `/topic`-style Telegram input, reusing whatever input pattern M2-105's manual-topic command already established rather than inventing a new one), produces a spec/architecture doc via `internal/llm`, and — once Mayank approves the idea — hands it to Builder (M2-501's planner) as a target repo/ticket set so `builder.plan` can run against it. This is the CONTEXT §2 line-2 income path ("Micro-SaaS / Chrome extensions built by Builder → recurring income") made concrete.

## Acceptance criteria
- [ ] `internal/micro_saas` (or wherever fits the existing package layout — flag if a different name/location is chosen) package: `idea.submit` job/handler that takes `{title, description, target_users, notes}` from manual input and creates a `content_items`-equivalent or purpose-built row tracking the idea through its stages (`submitted → spec_drafted → approved → handed_to_builder`). Confirm whether this reuses `content_items` (kind e.g. `"micro_saas_idea"`) or needs its own table — flag as a schema decision if a new table is chosen (append-only new migration, never edit `001_init.sql`).
- [ ] Generates a spec/architecture draft (the shape Builder's planner expects to read per M2-501: an `ARCHITECTURE.md`-and-`SPEC.md`-like document, or ticket list, in the target repo layout) via `internal/llm.Complete(ctx, task, req)`. **Flagged, not asserted:** which `task` name to route this under is genuinely unclear — ARCHITECTURE §6's task list is `research, script, metadata, translate_cleanup, classify, embeddings, blog, builder`, and CLAUDE.md is explicit that "Claude is for Builder and blog only." Since this spec directly feeds Builder's own planner (M2-501, already routed to Claude under task `builder`), reusing the existing `builder` task for "draft a spec from an idea" is the most defensible choice — but that task is currently scoped in M2-501 as "read an *existing* repo's ARCHITECTURE/SPEC/tickets and produce a subphase plan," not "invent a first-draft ARCHITECTURE/SPEC from a one-paragraph idea." Do not silently assume `builder` covers this; confirm with whoever owns `internal/llm`/M2-111, or add a distinct routed task (e.g. `builder_spec`) to `config.example.yaml`'s `llm.routes` map (currently only lists `blog: [claude]`, same gap M2-501 already flagged for `builder`) and document the choice here.
- [ ] Spec draft goes through `approval.request` exactly like every other publish/build path (D5) before anything is hidden from Mayank or handed off — Mayank approves the **idea + spec** once, the same one-tap pattern M2-501 uses for the subphase plan. Reject/Redo(note) re-runs the spec-drafting step with the note appended (same pattern as `script.write`/`blog.draft`/M2-501's plan redo).
- [ ] On approval, hands the approved spec to Builder as a target repo/ticket set: writes (or triggers M2-501's `builder.plan` to read) the `ARCHITECTURE.md`/`SPEC.md`/`tickets/*.md` shape in a target repo. **Flagged:** this requires a real target repo to exist and be listed in `config.builder.repos` (empty by default, per M2-501/CONTEXT §5 open question 1, still unanswered) — for a brand-new micro-SaaS idea there likely isn't an existing repo yet. This ticket should either (a) require the repo to already exist and be pre-registered in `config.builder.repos` before an idea can be handed off (simplest, defers repo-creation to Mayank), or (b) scaffold a new empty repo/directory and register it — pick (a) unless told otherwise, since repo creation/registration is a product decision outside this ticket's scope, and note the choice here.
- [ ] Once Builder (M2-501 onward) actually ships something for this idea (a `builds` row reaches its PR/complete state per M2-505), this flow is responsible for reminding Mayank a revenue entry is now expected — not for creating one automatically (a shipped repo isn't the same as first income; M2-601's `POST /api/revenue` stays a human/analytics-driven action). A daily-summary or dashboard nudge is enough; do not auto-fabricate a `revenue` row with a guessed amount.
- [ ] Table-driven tests next to the package: idea submission + stage transitions, spec-draft generation (fake LLM provider), approval-request creation, redo-with-note re-draft, refusal to hand off when the target repo isn't in `config.builder.repos`.
