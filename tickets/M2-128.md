## Goal
`internal/queue/worker.go`'s `runJob` has two call sites for `finalizeError`, and they disagreed on
which `maxAttempts` value to use to decide when a retrying job gets dead-lettered:

- The handler-no-longer-registered path (`job.Type` not found in `q.types`) correctly used
  `job.MaxAttempts` — the value frozen on the job's own row at `Enqueue` time
  (`internal/queue/queue.go` `Enqueue`, which inserts `reg.maxAttempts` into the row's `max_attempts`
  column once, at insert time).
- The normal handler-error path — the one every real job failure actually goes through — incorrectly
  used `reg.maxAttempts`, the **currently live** registration's value for that job type, looked up
  fresh from `q.types` on every failure via `q.lookup(job.Type)`.

Consequence: if a job type's registered `maxAttempts` is ever increased after some jobs are already
enqueued under the old, lower value (e.g. a job type going from `maxAttempts=3` to `maxAttempts=5`
across builds), jobs already in flight under the old value retry past their own row's `max_attempts`
cap instead of dead-lettering at it — the row's own frozen cap is silently ignored in favor of
whatever the currently-running binary happens to have registered for that type right now.

## Real-world evidence (read-only investigation, confirmed live)
Found via a read-only investigation of a test DB with live retrying jobs, not from a code read alone.
Two real rows, `jb-004` and `jb-007`, were observed retrying past their own row's `max_attempts`:
- Both rows' `max_attempts` column (frozen at their own `Enqueue` time) was lower than the value the
  currently-live binary has registered for their job type (`publish.youtube` / `analytics.pull` went
  from `maxAttempts=3` to `maxAttempts=5` across builds).
- Their observed retry/backoff timing matched `backoffFor` (1m / 5m / 30m / 2h, `internal/queue/
  worker.go`) exactly, attempt-for-attempt, past their own row's recorded cap — ruling out a one-off
  fluke or an unrelated bug. This is decisive: the backoff schedule is deterministic and keyed off
  `attempts`, so a match to the second attempt-over-attempt is only possible if `finalizeError` really
  is being called with a higher `maxAttempts` than the row's own column, exactly as the code read
  predicts.
- This confirms the two call sites' disagreement is not latent/theoretical — it was actively
  mis-behaving on real rows in the E2E test DB at investigation time.

## Fix
`internal/queue/worker.go` `runJob`: changed the normal handler-error path's `finalizeError` call from
`reg.maxAttempts` to `job.MaxAttempts`, matching the already-correct no-longer-registered path. Both
call sites now agree: the dead-letter decision always honors what was frozen on the row at `Enqueue`
time, never the live registration's current value.

```diff
-	q.finalizeError(finalizeCtx, job, workerID, reg.maxAttempts, err)
+	q.finalizeError(finalizeCtx, job, workerID, job.MaxAttempts, err)
```

## Notes

### Why this is real, not a misreading
Read `internal/queue/worker.go` and `internal/queue/queue.go` in full before touching anything:
- `queue.go` `Register` stores `maxAttempts` into `q.types[jobType].maxAttempts` — the **current**
  value for that type, overwritten every time the binary restarts with the current build's call to
  `Register`.
- `queue.go` `Enqueue` reads `reg.maxAttempts` at insert time and writes it into the new row's
  `max_attempts` column once (`INSERT INTO jobs (..., max_attempts, ...) VALUES (..., reg.maxAttempts,
  ...)`). From that point on, the row's `max_attempts` is frozen — it does not track future changes to
  the live registration.
- `worker.go` `scanJob` scans that frozen column into `Job.MaxAttempts` on every claim.
- `worker.go` `runJob`'s no-longer-registered branch (handler missing from `q.types`) already used
  `job.MaxAttempts` — correct, because `reg` doesn't even exist in that branch. The normal-error branch
  had a live `reg` in scope from the earlier `q.lookup(job.Type)` call and used `reg.maxAttempts`
  instead of `job.MaxAttempts` — the actual bug, now fixed to match the other branch.
