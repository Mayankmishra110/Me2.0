## Goal
`internal/revenue` is the single place every dollar/rupee entering the pipeline gets recorded: ad revenue reported from YouTube/Meta analytics (M2-212 already pulls YouTube Analytics metrics into `metrics`/`scores`; this ticket adds pulling/estimating the revenue-relevant figures into the `revenue` table), plus manual affiliate/sponsor/agency/saas entries added via the dashboard or Telegram. Serves `GET/POST /api/revenue` (SPEC §4, already documented and already stubbed to return an empty list in M2-106's `routes.go`) and gives the dashboard a Revenue screen with real entries on it — this is the concrete demonstration of SPEC §1's P6 exit check ("Revenue screen shows real entries"), and the foundation M2-602/603/604 each write one row into once they produce income.

**Schema check done before writing this ticket:** the `revenue` table already exists — `migrations/001_init.sql` (written by M2-102, `status: done`) on `phase/p1-foundation` already has `CREATE TABLE revenue (id, line CHECK IN ('ads','affiliate','agency','saas','sponsor'), source, amount, currency DEFAULT 'USD', date, note)` matching ARCHITECTURE §4 exactly. **No new migration should be needed for the base table** — verify this is still true on whatever `main` looks like at claim time (M2-102 hasn't landed on `main` yet per D25; confirm the table is there once its PR merges, or migrate it in per the M2-116 pattern of "verify current package/schema state again at claim time"). See Notes for whether the column set is enough to satisfy "every entry is attributable."

## Acceptance criteria
- [ ] `internal/revenue` package: `Entry` type mirroring the `revenue` table; `Record(ctx, Entry) (id string, err error)` (used by both manual API/Telegram input and the auto-pull path below); `List(ctx, filter) ([]Entry, error)` with filters at least on `line` and a date range.
- [ ] `GET /api/revenue` (wired into `internal/httpapi/routes.go`, replacing the empty-list stub from M2-106) returns entries, newest first, optionally filtered by `line`/date range per query params.
- [ ] `POST /api/revenue` accepts `{line, source, amount, currency, date, note}`, validates `line` against the same enum as the DB `CHECK` constraint, rejects missing `source`/`amount`/`date` (every entry must be attributable: source, date, amount — see Notes on whether `status` needs its own column), writes via `Record`, emits an `events` row (`revenue.recorded`) so it shows live on the dashboard via SSE.
- [ ] Auto-pull path: a `revenue.pull` (or equivalent) step that, alongside M2-212's existing `analytics.pull` (+24h/+7d), reads whatever revenue-relevant figures the YouTube Analytics API exposes for the channel (see Notes — exact metric/scope needs verification) and/or Meta's insights, and writes/updates a `line: "ads"` entry per channel per period with `source` identifying the channel and platform. This must not double-count: re-running the pull for a period that already has an entry updates it (idempotent on channel+platform+period), never inserts a duplicate row.
- [ ] Manual entry surfaces: dashboard `RevenuePage.tsx` (new page, following the existing `*Page.tsx` convention — `HomePage.tsx`, `ApprovalsPage.tsx`, `LogsPage.tsx`, `BuilderPage.tsx` once M2-505 lands — this convention currently lives on `phase/p1-foundation`/pending M2-505; match it rather than inventing a different shape) with a totals-by-line summary and a table of entries, plus a simple add-entry form (line, source, amount, currency, date, note) posting to `POST /api/revenue`. Wired into `web/src/App.tsx`'s route table and `web/src/components/layout/Nav.tsx` (desktop sidebar + mobile bottom tabs) as a real `/revenue` entry (this ticket is what should flip any placeholder/disabled nav entry for it, if one already exists from M2-107's shell).
- [ ] Telegram manual entry: flagged as a nice-to-have, not a hard requirement of this ticket (see Notes — `internal/telegram/commands.go`'s fixed command set is owned by M2-105, `status: done`; adding a `/revenue` command touches a file outside this ticket's `touches`). If implemented, it must follow the exact same allowlist/no-shell/fixed-argv rules as every other command (ARCHITECTURE §7) and needs a follow-up note in `internal/telegram`'s own history, not a silent edit.
- [ ] Every entry (manual or auto-pulled) carries source, date, and amount at minimum, and status is inferable (auto-pulled ad rows vs. manually-entered affiliate/sponsor/agency/saas rows) so the P6 exit check is concretely testable by reading the Revenue screen or querying `GET /api/revenue`.
- [ ] Table-driven tests next to `internal/revenue/`: `Record`/`List` round-trip and filtering, `POST` validation (bad `line`, missing fields), idempotent auto-pull update-not-duplicate, `events` row emitted on record. Frontend: component test for `RevenuePage.tsx` against a mocked `/api/revenue` response (MSW pattern from `web/src/mocks/`), covering empty state and a populated list with a totals summary.

## Notes
- **Flagged, not asserted:** the `revenue` table's current columns (`id, line, source, amount, currency, date, note`) cover source/date/amount but have **no explicit `status` column** (e.g. `pending` vs. `confirmed`/`received`). The brief for this batch of tickets requires every entry be attributable by "source, date, amount/status." Two options, pick one at implementation time and record the choice here: (a) treat all recorded entries as already-confirmed facts (ad revenue pulled from analytics, affiliate/sponsor amounts entered after the fact) and skip a status column — `note` can carry free-text status if ever needed; or (b) add a new **append-only** migration (`002_revenue_status.sql` or similar — never edit the shipped `001_init.sql`, CLAUDE.md) adding a `status` column with a sensible default. Do not silently pick (a) without noting it — if Mayank later wants to track "invoiced but not paid" agency income (relevant once M2-603 exists), (b) will be needed.
- **Flagged, not asserted:** which YouTube Analytics API metric actually exposes ad revenue (`estimatedRevenue`, `estimatedAdRevenue`, etc. require the `yt-analytics-monetary.readonly` scope, separate from the scopes M2-211/M2-212 currently request) needs verification against current YouTube Analytics API docs before implementing the auto-pull — do not assume the existing M2-212 OAuth scope already covers it. If the monetary scope isn't already granted, this ticket may need to extend M2-211's OAuth consent (flag to Mayank if a new consent/re-auth is required, since that's real waiting time per CONTEXT §6). Meta (Instagram/Facebook) ad revenue is not directly queryable the same way for a Page/creator in most cases — if no clean API path exists, this ticket should fall back to manual Meta ad-revenue entries only and say so plainly rather than inventing an integration.
- **Not a D5 approval path.** Revenue entries are internal records, not public/outbound content, so `approval.request` doesn't apply here the way it does for publish/outreach tickets. Flagging this explicitly because the batch-level instruction ("every ticket that touches money or outbound content requires an approval step") is about outbound content and the *spending/sending* side of money (M2-602's Builder handoff, M2-603's outreach drafts, M2-604's pins) — this ticket only *records* revenue that already happened, so there's nothing to approve. If Mayank disagrees (e.g. wants to review auto-pulled figures before they count), that's a product decision — note it in CONTEXT.md's Open questions if it comes up.
- Telegram `/revenue` command: intentionally left as optional/deferred rather than in scope, since `internal/telegram/commands.go` belongs to M2-105 (already `done`, reviewed, shipped its own command set) and this ticket's `touches` doesn't include it. If the implementer wants Telegram manual entry, treat it the same way M2-116 flagged cross-package wiring gaps: either get explicit sign-off to extend `touches`, or leave it for a follow-up ticket and say so in CONTEXT.md.
- `internal/revenue` is a new top-level package not currently listed in ARCHITECTURE §9's repository layout (`config, db, queue, scheduler, events, telegram, httpapi, secrets, llm, content, compliance, media, publish, analytics, blog, builder, tickets, storage`). This ticket should add it to that list as part of "docs updated if behavior or decisions changed" (SPEC §7).
- This ticket's job-handler registration (if `revenue.pull` is implemented as a queue job rather than called inline from `analytics.pull`'s completion) needs wiring into `cmd/mayank2/run.go` — M2-116 (daemon wiring) was written before P6 existed, so its table of "who registers what" doesn't mention this. Note the gap in M2-116 or in CONTEXT.md if `revenue.pull` needs its own registration and M2-116 has already shipped by the time this is picked up.
