## Notes

### Technical decisions (be-4, 2026-09-28)
- **Video pin flow (verified):** Pinterest API v5 requires four steps for video ? `POST /v5/media` (`media_type: video`) ? multipart POST to returned `upload_url` with `upload_parameters` ? poll `GET /v5/media/{id}` until `succeeded` ? `POST /v5/pins` with `media_source.source_type: "video_id"`, `media_id`, and mandatory `cover_image_url`.
- **Cover URL:** `ThumbnailPath` is an R2 object key (or absolute http(s) URL); `pinPresigner.PresignGET` mints the temporary public cover URL (D20 / M2-213).
- **Board:** `PublishRequest.PlaylistID` carries the destination `board_id`. Per-topic boards remain a config/product choice outside this ticket.
- **Destination link:** first `http(s)` tag; cloaker hosts rejected fail-closed; affiliate disclosure appended when `PaidPromotion` is set.
- **Quotas:** `pinterest:<account>` daily cap 5; `pinterest_dest:<account>:<sha256-prefix>` limit 1 per UTC day.
- **OAuth:** business pin creation needs `pins:write` (+ `boards:read`); refresh failures and 401/403 surface `reauth needed` (permanent in the job handler). Daemon wiring of `TokenSourceFor` ? `internal/secrets` follows the same deferred pattern as M2-211.
- `needs-sec: yes` ? OAuth tokens, publish path, path confinement, R2 cover URLs.

### Independent qa+sec audit — 2026-09-28 (crew qa+sec)

Did not trust the prior `## Review` verdicts above at face value — re-read `pinterest.go` end to end
myself, including the two extra checks this audit specifically asked for (cloaker-before-any-API-call,
disclosure-as-real-check-vs-comment).

**QA: pass** — 2026-09-28 — Traced `Publish()` (pinterest.go:98-199): `content.RequireApproved`
(line 113) runs before `lookupPublished` (116, idempotency), both run before any Pinterest API call
(`RegisterMedia`, line 167 — the first HTTP call in the whole flow). Idempotency lookup genuinely
precedes the media-register-equivalent of a "container create" call.

**SEC: pass** — 2026-09-28 —

1. **No-link-cloaker check runs before any API call.** `link := pinDestinationLink(req.Tags)` /
   `looksLikeCloaker(link)` (pinterest.go:122-125) sits immediately after the idempotency lookup (116)
   and strictly **before** `reserveDest` (127), `reserveCap` (132), `markPublishing` (136), `p.token()`
   (140), and `RegisterMedia` (167). Confirmed: a cloaked link is rejected before the token is even
   fetched, let alone before any Pinterest API call — genuinely reject-first, not reject-after-attempt.
2. **Affiliate disclosure — precise answer to the question asked.** `pinDescription` (pinterest.go:457-463)
   unconditionally appends `pinAffiliateDisclosure` to the pin description server-side whenever
   `req.PaidPromotion` is true — this **is** real executable code, not a documentation-only comment, and
   a caller cannot omit the disclosure text once that flag is set (it's injected regardless of what the
   caller's `Description` field contains). But it is specifically **not** a "reject a pin missing
   disclosure" gate as literally asked — there is no validation path that fails a publish for missing
   disclosure; instead disclosure presence is guaranteed by unconditional server-side injection keyed
   off the caller-supplied `PaidPromotion` bool. There is no independent signal (e.g. detecting an
   affiliate-shaped destination link pattern) that would catch a pin where `PaidPromotion` was
   incorrectly left `false` upstream — the disclosure requirement is enforced *for* the flag's stated
   value, not independently *of* it. This exact nuance is already flagged non-blocking in the prior SEC
   pass above ("disclosure depends on PaidPromotion upstream"); this audit independently re-derived and
   confirms the same finding, with the precise framing this brief asked for.
3. **Token redaction — grepped every response-parsing path.** `pinDoJSON` (pinterest.go:609-632) redacts
   the body (line 618: `body = []byte(pinRedact(string(body)))`) **before** the 401/403 check (619),
   before `json.Unmarshal` (622-624), and before the generic ≥400 fallback (625-627) — all in one place,
   before every branch. `HTTPPinterestAPI.UploadMediaFile` (527-559), the one function that doesn't use
   `pinDoJSON` (it's a multipart upload, not JSON), also redacts inline before building its error (line
   556: `pinRedact(string(body))`) — it never unmarshals a structured error object from an unredacted
   body the way `facebook.go`'s `UploadHosted` does (see M2-302 finding, filed this same audit pass). No
   gap found in this file.
