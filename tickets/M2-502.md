## Goal
`builder.implement` job that, for one approved subphase, creates or reuses a git worktree in the target repo, runs `claude -p` headless (Opus 5.5, `config.builder.implementer_model`, per D7) with that subphase's plan file and ticket(s) as context, commits the resulting work on a build branch, and emits `subphase.done` so the Auditor (M2-503) can start on it while this job moves to the next subphase (D7's core parallelism). This job must never push to, check out, or otherwise modify the target repo's `main` branch (CLAUDE.md non-negotiable, ARCHITECTURE §7).

## Acceptance criteria
- [ ] `internal/builder/implementer.go` implements the `builder.implement` job: no-op when `config.builder.enabled` is `false`; refuses repos not in `config.builder.repos` (same gate as M2-501 — do not name specific repos).
- [ ] Creates a git worktree under `data/worktrees/<repo>/<branch>` (repo layout per ARCHITECTURE §9's `data/` note) if one doesn't already exist for this build's branch (`build/phase-N` per ARCHITECTURE §3.3); reuses it on subsequent subphases of the same plan. Worktree creation/removal uses fixed git argv, never a shell string built from AI output (CLAUDE.md non-negotiable).
- [ ] Runs `claude -p` (headless, non-interactive) in the worktree's working directory with `--model` set from `config.builder.implementer_model`, passing the subphase's plan/ticket content as context, honoring `config.builder.run_timeout` as a hard process timeout (fixed timeout on every child-process call, CLAUDE.md non-negotiable).
- [ ] Applies the Builder tool/Bash allowlist from ARCHITECTURE §7: `git push`, `git reset --hard`, and edits to `.env*` are denied to the Claude session. Flag in code comments and in this ticket's Notes exactly how that denial is enforced (see Notes — this needs confirming against the real CLI).
- [ ] **Hard acceptance criterion with a test:** this job never pushes to, checks out `main` for commits on, force-pushes, or fast-forwards the target repo's `main` branch, under any code path — including failure/retry paths. Test asserts (against a local fake/temp-dir git remote) that after a run, `main`'s ref is byte-identical to before the run, and that no `push`/`checkout main`/`merge`-to-main git invocation was ever issued (assert on the fixed-argv command list actually built, not just the mocked exit code).
- [ ] On successful completion of a subphase: commits the worktree's changes on the build branch with message `N.M: <summary>` (fixed argv `add`/`commit`, never a shell string from Claude's output) and emits a `subphase.done` event (`internal/events`) carrying repo/plan/subphase identifiers, which M2-503 subscribes to.
- [ ] On `config.builder.run_timeout` exceeded or a detected Claude Pro usage-limit response: returns a distinguishable error/state so M2-504 (phase gate) can apply the fix-retry or pause logic — this job does not itself decide retry vs. pause, it just reports what happened.
- [ ] Table-driven tests next to the file: enabled/disabled gate, repo-not-listed rejection, worktree create-then-reuse, never-touches-main (above), timeout produces the distinguishable timeout result, `subphase.done` event emitted with correct payload on success.

## Notes
- **Flagging real uncertainty, not asserting confidently:** `internal/llm/claude.go` (M2-111, on `phase/p1-foundation`) already wraps `claude -p --output-format json [--model X]` as a single-shot text-completion provider (stdin prompt in, `{result|content|text}` JSON out) — that pattern is right for `research`/`script`/`blog`-style one-shot generation, but the Implementer needs a genuine autonomous **coding session**: reading/editing/writing files and running shell commands inside the worktree over what is likely several turns, not a single prompt/response. The real `claude -p` CLI's flags for this use case — tool/permission allowlisting (e.g. something like `--allowedTools`/`--permission-mode`, or a settings file), how `--output-format json` behaves across a multi-tool session, whether the working directory is set via `cwd` on the child process or a CLI flag, and how a Pro usage-limit hit actually surfaces in stdout/stderr/exit code for this invocation shape — are **not established anywhere in this repo**. Do not assume `internal/llm.Complete`/`claudeCLIProvider` can be reused as-is for this job; check the real `claude -p` CLI behavior (`claude -p --help`, current docs) before implementing, and note what was actually found/used in this ticket's Notes once built.
- Which repos Builder may touch is still open (CONTEXT.md §5, question 1). Everything here is driven by `config.builder.repos` (empty by default) and `config.builder.enabled: false` — don't guess or hardcode a repo name in code, tests, or this ticket.
- The "denies `git push`/`git reset --hard`/`.env*` edits" allowlist in ARCHITECTURE §7 is stated as a requirement but the mechanism (Claude Code's own permission/settings config vs. this job additionally sandboxing the worktree itself, e.g. a read-only `.git/config` trick or a pre-commit hook) isn't specified. Whatever this ticket implements, the **hard, tested** guarantee is "never touches `main`" (the AC above) — treat the broader allowlist as defense in depth and document which parts are enforced by Claude Code's own config vs. by this job's own checks.
