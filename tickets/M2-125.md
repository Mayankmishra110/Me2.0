## Goal
Found by a live end-to-end audit (HIGH severity): `POST /api/login` works correctly server-side
(`internal/httpapi/auth.go`), but nothing in `web/src/` real app code ever calls it — only the MSW mock
handler does (`web/src/mocks/handlers.ts:190`, pre-fix). `App.tsx` had no `/login` route and `AppShell`
rendered the full dashboard shell unconditionally regardless of auth state. A human opening the dashboard
with no session cookie had no way to ever authenticate; the token could only be exchanged for a session
via curl/Postman. Add a real login screen and gate the dashboard behind it.

## Acceptance criteria
- [x] `/login` route renders a real login form: one token input, submit button, calls `POST /api/login`
  with `{ token }` (contract read from `internal/httpapi/auth.go`'s `loginRequest`).
  Proved: `src/pages/LoginPage.tsx`; `src/pages/LoginPage.test.tsx` asserts the exact POST body.
- [x] Success (sets the HttpOnly session cookie, `{ ok: true }`) redirects to `/` or wherever the visitor
  was headed before being bounced to `/login`.
  Proved: `LoginPage.test.tsx` "redirects to / on success" and "redirects back to the originally requested page".
- [x] Failure: 401 → "Incorrect token"; network/other error → generic retry message. 429 (login rate limit,
  `auth.go` `loginMaxAttempts`) shown distinctly too.
  Proved: `LoginPage.test.tsx` 401 and network-error cases.
- [x] Dashboard shell gated: unauthenticated visitors are redirected to `/login` instead of seeing `AppShell`.
  `/api/health` is public (SPEC §4) so it can't answer "is this session valid" — reused `GET /api/agents`,
  the cheapest endpoint already behind `requireAuth`, instead of inventing a new backend contract.
  Proved: `src/components/auth/RequireAuth.tsx`; `RequireAuth.test.tsx` (unauthenticated → `/login`,
  authenticated → dashboard, no redirect).
- [x] A 401 on any API call mid-session (expired session) redirects to `/login` instead of a broken page.
  Proved: `src/api/authEvents.ts` pub/sub, wired into `apiFetch` (client.ts) and a router-mounted listener
  in `App.tsx`; the login call itself passes `skipAuthEvent: true` so a failed login doesn't also fire a
  same-page redirect.
- [x] Visual style matches existing pages/tokens (DESIGN §1.3), mobile-first.
  Proved: reuses `Card`/`Button` from `src/components/ui/`; new `Input` follows the same `cva`-free
  token-based pattern as `button.tsx`/`switch.tsx`; single-column, `min-h-11` touch targets.
- [x] Tests: login form component test (submit → correct endpoint/payload → success redirects, failure
  shows error) + routing test (unauthenticated `/` → `/login`, authenticated `/` stays).
  Proved: `LoginPage.test.tsx` (4 tests), `RequireAuth.test.tsx` (2 tests), using existing MSW
  `server.use(...)` override patterns from `src/mocks/`.

## Notes

### Auth-check mechanism
`GET /api/agents` — already behind `s.requireAuth` in `internal/httpapi/routes.go`, trivial response
(`{ agents: [] }` today), and already consumed by `useAgents()`. `useAuthStatus()` in `src/api/hooks.ts`
reuses the exact same query key (`queryKeys.agents`) so `RequireAuth` and `HomePage` share one cached
request instead of firing two. No new backend endpoint was added — reused what SPEC §4 already exposes.
`/api/health` was considered but is explicitly public in `routes.go` (`mux.HandleFunc("GET /api/health", ...)`
is registered before the `requireAuth` wrapper), so it can never answer the "is my cookie valid" question.

### Why needs-sec: no
Client-side UI calling an already-existing, already-authenticated server endpoint (`POST /api/login`,
shipped and tested in `internal/httpapi/auth_test.go`). No new credential path, no new cookie flags, no
change to `internal/httpapi/auth.go` at all — this ticket is pure `web/` routing/UI. The only behavior
change on the Go side is none; `requireAuth` already rejected unauthenticated requests with 401, the
dashboard simply didn't have anywhere to send people in response to that 401 before.

**1 real gap found** (the exact "could this loop / omit skipAuthEvent" scenario the ticket
calls out, and the shipped tests don't catch it because they render `LoginPage`/`RequireAuth`
standalone, never together with the `UnauthorizedRedirect` listener `App.tsx` actually mounts):

`useAuthStatus()` (`web/src/api/hooks.ts:46-51`) is called from **two** places: `RequireAuth.tsx:17`
(the route guard) and `LoginPage.tsx:21` (LoginPage's own "am I already logged in" check, so it
can skip the form). Neither call passes `skipAuthEvent`. `apiFetch` (`web/src/api/client.ts:36`)
fires the global `emitUnauthorized()` on **any** unflagged 401 — including this one.

Trace for the ordinary case (unauthenticated visitor hits a protected route, e.g. `/approvals`):
1. `RequireAuth`'s `useAuthStatus()` 401s → `RequireAuth` renders `<Navigate to="/login" replace
   state={{from: location}}/>` (preserves `/approvals`).
2. `LoginPage` mounts. Its *own* `useAuthStatus()` call (same query key, but React Query refetches
   on mount for a query that previously errored, since it has no `dataUpdatedAt`) 401s again.
3. That second 401 is unflagged → `emitUnauthorized()` fires → `App.tsx`'s `UnauthorizedRedirect`
   (`App.tsx:29-33`) calls `navigate('/login', { replace: true })` with **no state** —
   overwriting the `location.state.from` that step 1 had just set.
4. `LoginPage`'s `redirectTo` (`LoginPage.tsx:24`) is read from `location.state`, so after the
   clobber it falls back to `/`. The user logs in successfully but lands on the dashboard home
   instead of `/approvals`, silently breaking acceptance criterion #2
   ("redirects to ... wherever the visitor was headed before being bounced to `/login`").

I reproduced this directly (not just read-and-infer): built a temporary test rendering
`LoginPage` together with the same `onUnauthorized`-listener wiring `App.tsx` uses (not present
in any shipped test file), with `location.state.from.pathname = '/approvals'` and `/api/agents`
returning 401. Result: after a successful login, the page shows "Dashboard home", not "Approvals
screen" — confirming the clobber. (Temp file was not committed; removed after confirming.)

Not an infinite redirect loop (query has `retry: false`, and re-navigating to the already-current
`/login` doesn't cause a render loop) — but it is a real, reproducible contract break, and it's
silent: nothing errors, the user just loses their intended destination.

**Fix needed:** `LoginPage.tsx:21`'s `useAuthStatus()` call is checking "am I already logged in,"
not "did my session just expire" — it's the same kind of routine, expected 401 that `useLogin`
already exempts via `skipAuthEvent`. Either (a) add a `skipAuthEvent`-equivalent option to
`useAuthStatus`/`apiFetch` so `LoginPage`'s own check doesn't emit the global event (cleanest —
mirrors the existing `useLogin` pattern), or (b) have `UnauthorizedRedirect` no-op when
`location.pathname` is already `/login` *and* preserve existing `state` instead of dropping it,
so a stray event can't erase a destination that was already set. Prefer (a): it fixes the root
cause (a benign check firing a session-expiry signal) rather than papering over the symptom.
Add a regression test modeled on the repro above (mount `LoginPage` + the `onUnauthorized`
listener together, with `location.state.from` pre-set and `/api/agents` 401ing) so this can't
regress silently again.

### Fix for QA gap — 2026-10-04

`useAuthStatus` into the underlying `apiFetch` call, matching the existing `useLogin` pattern.

- `web/src/api/hooks.ts`: `useAuthStatus()` now takes an optional `{ skipAuthEvent?: boolean }`
  and passes it through to `apiFetch('/api/agents', { skipAuthEvent })`. `RequireAuth.tsx`'s call

  401 there still fires the global unauthorized event as intended).

  probe) now passes `useAuthStatus({ skipAuthEvent: true })`, so a 401 there is treated the same
  routine way `useLogin`'s own 401 already is — it no longer fires `emitUnauthorized()` and can
  no longer clobber a `location.state.from` that `RequireAuth` just set.
