## Goal
Found by a live end-to-end audit (HIGH severity): `POST /api/login` works correctly server-side
(`internal/httpapi/auth.go`), but nothing in `web/src/` real app code ever calls it — only the MSW mock
handler does (`web/src/mocks/handlers.ts:190`, pre-fix). `App.tsx` had no `/login` route and `AppShell`
rendered the full dashboard shell unconditionally regardless of auth state. A human opening the dashboard
with no session cookie had no way to ever authenticate; the token could only be exchanged for a session
via curl/Postman. Add a real login screen and gate the dashboard behind it.

## Acceptance criteria
- [x] `/login` route renders a real login form: one token input, submit button, calls `POST /api/login`
  with `{ token }` (contract read from `internal/httpapi/auth.go`'s `loginRequest`).
  Proved: `src/pages/LoginPage.tsx`; `src/pages/LoginPage.test.tsx` asserts the exact POST body.
- [x] Success (sets the HttpOnly session cookie, `{ ok: true }`) redirects to `/` or wherever the visitor
  was headed before being bounced to `/login`.
  Proved: `LoginPage.test.tsx` "redirects to / on success" and "redirects back to the originally requested page".
- [x] Failure: 401 → "Incorrect token"; network/other error → generic retry message. 429 (login rate limit,
  `auth.go` `loginMaxAttempts`) shown distinctly too.
  Proved: `LoginPage.test.tsx` 401 and network-error cases.
- [x] Dashboard shell gated: unauthenticated visitors are redirected to `/login` instead of seeing `AppShell`.
  `/api/health` is public (SPEC §4) so it can't answer "is this session valid" — reused `GET /api/agents`,
  the cheapest endpoint already behind `requireAuth`, instead of inventing a new backend contract.
  Proved: `src/components/auth/RequireAuth.tsx`; `RequireAuth.test.tsx` (unauthenticated → `/login`,
  authenticated → dashboard, no redirect).
- [x] A 401 on any API call mid-session (expired session) redirects to `/login` instead of a broken page.
  Proved: `src/api/authEvents.ts` pub/sub, wired into `apiFetch` (client.ts) and a router-mounted listener
  in `App.tsx`; the login call itself passes `skipAuthEvent: true` so a failed login doesn't also fire a
  same-page redirect.
- [x] Visual style matches existing pages/tokens (DESIGN §1.3), mobile-first.
  Proved: reuses `Card`/`Button` from `src/components/ui/`; new `Input` follows the same `cva`-free
  token-based pattern as `button.tsx`/`switch.tsx`; single-column, `min-h-11` touch targets.
- [x] Tests: login form component test (submit → correct endpoint/payload → success redirects, failure
  shows error) + routing test (unauthenticated `/` → `/login`, authenticated `/` stays).
  Proved: `LoginPage.test.tsx` (4 tests), `RequireAuth.test.tsx` (2 tests), using existing MSW
  `server.use(...)` override patterns from `src/mocks/`.

## Notes

### Auth-check mechanism
`GET /api/agents` — already behind `s.requireAuth` in `internal/httpapi/routes.go`, trivial response
(`{ agents: [] }` today), and already consumed by `useAgents()`. `useAuthStatus()` in `src/api/hooks.ts`
reuses the exact same query key (`queryKeys.agents`) so `RequireAuth` and `HomePage` share one cached
request instead of firing two. No new backend endpoint was added — reused what SPEC §4 already exposes.
`/api/health` was considered but is explicitly public in `routes.go` (`mux.HandleFunc("GET /api/health", ...)`
is registered before the `requireAuth` wrapper), so it can never answer the "is my cookie valid" question.

### Why needs-sec: no
Client-side UI calling an already-existing, already-authenticated server endpoint (`POST /api/login`,
shipped and tested in `internal/httpapi/auth_test.go`). No new credential path, no new cookie flags, no
change to `internal/httpapi/auth.go` at all — this ticket is pure `web/` routing/UI. The only behavior
change on the Go side is none; `requireAuth` already rejected unauthenticated requests with 401, the
dashboard simply didn't have anywhere to send people in response to that 401 before.
