## Goal
Once every subphase in a plan has been gated `pass` (M2-504), `internal/builder/pr.go` pushes the build branch (never `main`) and produces a PR/compare link, sent to Mayank via Telegram (ARCHITECTURE §3.3: "push branch → PR/compare link → Telegram"). `web/src/pages/BuilderPage.tsx` is the dashboard screen from DESIGN.md's Builder row: per-repo plan tree (phases → subphases) with status, two live panes **Implementer** and **Auditor** (current subphase, last output lines, session cost/limit), audit findings, and PR links — reading `GET /api/builder` (SPEC §4, already documented and already stubbed to return an empty list in M2-106's `routes.go` until this module exists).

## Acceptance criteria
- [ ] `internal/builder/pr.go`: after M2-504 marks the last subphase of a plan gated `pass`, pushes the build branch to the target repo's remote (fixed git argv `push origin <branch>`, never `--force`, never any argv targeting `main`) — reuses the "never touches `main`" guarantee already required of M2-502/M2-503; add the same test shape here (branch pushed is never `main`, no `main`-targeting git invocation).
- [ ] Produces a PR or compare link and records it on the `builds` row (`pr_url` column, already in the ARCHITECTURE §4 schema). **Flagged uncertainty:** no ticket in this repo (`M2-101`…`M2-404`) establishes how a PR actually gets opened against a target repo — whether via `gh pr create` (would need `gh` installed/authenticated for the *target* repo, not this one), the GitHub REST API with a token from `internal/secrets`, or simply a `https://github.com/<owner>/<repo>/compare/main...<branch>` link with no API call at all (cheapest, no new credential, but no PR body/reviewers). Do not assume one silently — this ticket should confirm with Mayank which mechanism he wants (and, if API-based, that a GitHub token for the *target* repo exists in the secrets vault) before or during implementation, and record the decision in this ticket's Notes and/or CONTEXT.md's decision log if it changes a decision.
- [ ] `builder.enabled: false` / repo-not-in-`builder.repos` gates this job exactly as in M2-501–504 — do not name specific repos in code or tests.
- [ ] `web/src/pages/BuilderPage.tsx`: new page following the existing `*Page.tsx` convention in `web/src/pages/` (`HomePage.tsx`, `ApprovalsPage.tsx`, `LogsPage.tsx`, `MorePage.tsx` — this convention lives on `phase/p1-foundation` since M2-107 built the shell there and it hasn't landed on `main` yet; match it rather than the literal `Builder.tsx` name).
- [ ] Wires the page into `web/src/App.tsx`'s route table (`<Route path="builder" element={<BuilderPage />} />`, alongside the existing `approvals`/`logs`/`more` routes) and enables the already-present-but-`disabled: true` `/builder` nav entry in `web/src/components/layout/Nav.tsx` (both the desktop `Sidebar` and mobile `BottomTabs` lists reference it).
- [ ] `BuilderPage.tsx` fetches `GET /api/builder` via TanStack Query (matching the existing `web/src/api/hooks.ts` pattern) and renders: a plan tree per repo (phases → subphases, each with status), an Implementer pane and an Auditor pane (current subphase, last output lines, session cost/limit — per DESIGN.md), an audit-findings list, and PR links once available. Uses design tokens from DESIGN.md §1.3 per CLAUDE.md's web conventions; mobile-first.
- [ ] Handles the empty/not-yet-built-out API response gracefully (M2-106 already ships `GET /api/builder` returning an empty list) — the page must render a sensible empty state today, before `internal/builder` exists at all, not just once M2-501–504 land.
- [ ] Tests: `internal/builder/pr.go` table-driven tests (enabled/disabled gate, repo gate, push-never-targets-main, `pr_url` recorded on the `builds` row); a component/rendering test for `BuilderPage.tsx` against a mocked `/api/builder` response (following the existing MSW mock pattern in `web/src/mocks/`), covering both the empty state and a populated plan/audit example.
