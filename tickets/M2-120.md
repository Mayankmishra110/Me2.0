## Goal
`POST /api/topics` was a pure echo (decode body, return it back) with no DB or queue effect — the one
manual entry point SPEC §4 defines for a human to add a topic outside the automatic daily `scout.topics`
discovery run did nothing. `GET/POST /api/topics` now read and write real `topics` rows.

## Acceptance criteria
- [x] `POST /api/topics` validates `{channel_id, title, source_url?}`: non-empty `channel_id` that
      references a real `channels` row, non-empty `title` capped at 200 chars with no control
      characters, optional `source_url` capped at 2000 chars and must be `http(s)`.
- [x] Valid `POST /api/topics` writes a real `topics` row (`source='manual'`, `status='new'`) and returns
      the created record (id, channelId, title, source, sourceUrl, score, status, createdAt) — not an
      echo of the request body.
- [x] Duplicate manual topic (same channel, same normalized title) within the scout dedup window is
      refused with 400, matching `content.Scout.AddManual`'s existing dedup behavior.
- [x] `GET /api/topics` lists real rows from the `topics` table, filterable by `channel_id`/`status`,
      capped `limit`.
- [x] Both routes stay behind `requireAuth` (already true in `routes.go`; confirmed by test, not weakened).
- [x] Table-driven tests: valid topic → 201 + real DB row; empty/oversized/malformed/unknown-channel
      body → 400; unauthenticated → 401.

### Data flow decision (technical, not product-ambiguous — no CONTEXT.md entry needed)

`docs/SPEC.md` §4 lists `GET/POST /api/topics` as the manual counterpart to the automatic
`scout.topics` job. `internal/content/scout.go` (M2-202) already defines exactly this: `Scout.AddManual`
whose doc comment literally says "(Telegram `/topic` and dashboard `POST /api/topics`)". Its behavior
answers the "does a manual topic skip Niche Scout's scoring or feed into it" question already: a manual
topic gets a **fixed high-confidence signal set** (`Demand=0.8, Freshness=1.0, Fit=1.0, Competition=0.2`)
times `content.DefaultScoutManualBoost` (1.5x), written into the same `topics` table with
`source='manual'` — it is not injected back into Niche Scout's discovery inputs, and it does not directly
enqueue a `research.brief`/`scout.topics` job either. It just seeds the same table the (not-yet-wired,
M2-119) research stage will read `status='new'` rows from next. This ticket follows that exact convention
rather than inventing a second path.

**Implementation note:** this ticket does not call `content.Scout.AddManual` directly. `content.NewScout`
requires a configured signal source (`YouTubeAPIKey` or `RSSFeeds`) to construct at all — a requirement
that makes sense for the background discovery `Run()` but is orthogonal to accepting one manually typed
topic, and would make this endpoint fail whenever no discovery source is configured (contradicts D24:
"everything runs with only the keys you have"). `touches` for this ticket is also `internal/httpapi/`
only, so I didn't relax that constructor requirement in `internal/content`. Instead
`internal/httpapi/topics.go` reproduces `AddManual`'s exact scoring/dedup formula inline (same constants,
including the exported `content.DefaultScoutManualBoost` / `content.DefaultScoutDedupWindow` /
`content.TopicSourceManual` / `content.TopicStatusNew`, so the boost/window values stay single-sourced
from `internal/content`), and writes straight into the `topics` table with the same shape
`Scout.insertTopic` uses. If a future ticket relaxes `NewScout`'s construction requirement (own ticket,
touches `internal/content/`), this handler could switch to calling `AddManual` directly with no schema
change.

Input sanitization (CLAUDE.md: never build a shell string from AI output, and this becomes downstream
LLM/pipeline input): title capped at 200 runes, any Unicode control character (including NUL, tab,
newline) rejected outright — titles are single-line. `source_url` capped at 2000 chars, must parse as an
`http`/`https` URL with a host (rejects `javascript:`, `file:`, bare paths). Neither field is ever passed
as a shell/process argument anywhere in this change.

`needs-sec: no` — authenticated internal endpoint already behind `requireAuth` (confirmed unchanged), no
external platform calls, no secrets touched. Still validated input per the general bar.

   **But the dedup key itself has drifted.** `scout.go:568-573` `normalizeTitle`:

   var nonAlpha = regexp.MustCompile(`[^a-z0-9\s]+`)
   func normalizeTitle(s string) string {
       s = strings.ToLower(strings.TrimSpace(s))

   `content.Scout.AddManual`'s behavior." It is a real behavioral drift, not just a style nit — it lets a
   duplicate through in a case the ticket explicitly says is covered, and the existing test suite doesn't
   catch it because `TestTopicsCreateAndList`'s duplicate case (`"budgeting for beginners"` vs
