**What changed (`g7.go`)**
- `G7.Check` no longer falls straight to `Passed: true` for English when `Classifier` is nil. It now runs
  `englishReadabilityHeuristic`, four independent, real (non-LLM) signals, any one of which can fail the
  gate on its own:
  1. Immediate word repetition ("the the", stutter/broken-generation signal), language-agnostic and
     separate from the existing `hiArtifacts` list.
  2. Filler/hedge-word density ("um", "uh", "basically", "literally", "honestly", "you know", "kind of",
     "sort of", "i mean", "at the end of the day", etc.) — single words matched as whole punctuation-trimmed
     tokens (not raw substrings, so "um" doesn't false-positive inside "document"); fails above 6% density
     once the script has ≥15 words.
  3. Repeated/looping n-gram detection (same 4-word phrase ≥3 times) — catches templated or stuck
     generation.
  4. Run-on-sentence check — a single sentence (no `.`/`!`/`?`) over 45 words fails as poor reading level.
  - When `Classifier` is set, its verdict still runs after the heuristic and is authoritative in both
    directions (pass-overrides-heuristic-fail and fail-overrides-heuristic-pass) — same relationship G5
    already had between its heuristic and its classifier.
  - Hindi path (`hiArtifacts` + Devanagari-ratio check) is untouched.
  - No production wiring existed anywhere to change (`compliance.NewEngine(` has zero non-test call sites
    in the tree today — reconfirmed), so no other file needed to change; `LLMClassifier`/`RouterEmbedder`
    in `llm_adapters.go` already exist for whoever wires a real classifier through `internal/llm` later
    (M2-111's `llm.TaskClassify` route is ready for this).

**Why heuristic-only (option b), not fail-closed-on-nil (option a)**
- This ticket's `touches` is `internal/compliance/` only. The only place that constructs an `Engine` in
  the whole tree is `NewEngine` itself (called only from its own package and from tests) — there is no
  existing call site in `cmd/` or elsewhere that passes a classifier, and there is no config flag
  anywhere (`Thresholds` has none) that says "a classifier is expected/configured." So there is no
  present distinction in this codebase between "no classifier by design" and "classifier expected but
  broken" — the ambiguity flagged in the assignment doesn't exist yet in the code as written. Making
  `NewEngine`/G5/G7 refuse outright on `Classifier == nil` today would just make the *whole engine*
  fail-closed always (since nothing anywhere constructs it with a real classifier yet), which contradicts
  COMPLIANCE §3's own G5/G7 rows (LLM judge is the *default* threshold, not a hard requirement gating all
  other gates) and would regress G5's already-accepted (QA/SEC-passed) nil-heuristic behavior for no
  reason. Matching G5's existing, previously-reviewed pattern (`Classifier == nil` → real heuristic;
  `Classifier` present → its verdict is authoritative) is therefore the correct read of "match G5's
  pattern," per the assignment's own instruction — and is a same-day feasible, real fix within scope,
  vs. wiring `internal/llm.Complete(TaskClassify, ...)` into a production call site, which lives outside
  `internal/compliance/` and outside this ticket's `touches`.
- If a future ticket adds a config flag or wiring path that says "a classifier must be present here,"
  that ticket should add the fail-closed-on-missing-classifier check at that call site (or here, if it
  turns out to belong in this package) — flagging this as a fair follow-up rather than silently deciding
  it.
