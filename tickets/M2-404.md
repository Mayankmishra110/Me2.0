## Goal
Per CONTEXT D19 (Medium has no usable publishing API), package the canonical Mayankbuilt post into whatever Medium's "Import a story" flow needs and deliver it as a one-tap link via Telegram/dashboard. Mayank completes the import himself in Medium's own UI — this ticket does **not** publish to Medium.

## Acceptance criteria
- [x] `internal/blog/medium.go` implements the Medium leg triggered after M2-401's `blog.merge` succeeds: reads the now-live canonical post's public URL from `publications` (`platform = "mayankbuilt"`). Proven by `Medium.canonicalPublicURL` (`SELECT url FROM publications WHERE content_id=? AND platform='mayankbuilt' ...`) + `TestMedium_Handle_SendsLinkAndRecords`, `TestMedium_Handle_NoPublicationYetIsRetryable`.
- [x] Builds Medium's "Import a story" URL from that public URL (Medium's import flow historically accepts the source article URL as a query parameter — exact current parameter name/path not fully certain, see Notes). No OAuth, no API call, no token of any kind is used, since none exists (D19). Proven by `BuildImportURL` (`medium.com/p/import?url=<source>`) + `TestBuildImportURL` table (9 cases incl. trailing slash, query-string re-encoding, http scheme, empty/whitespace/relative/unsupported-scheme/no-host errors). No network call, no token field anywhere in this file.
- [x] Sends the import link to Mayank via Telegram (a message with an inline button/link, same delivery mechanism as approval prompts) and surfaces it on the dashboard (e.g. alongside the content detail view for that post). Telegram leg proven by `Medium.Handle` calling the same `telegram.Client.SendMessage` M2-105 uses (via the `TelegramSender` interface, which `*telegram.Client` satisfies directly — no parallel delivery path) + `TestMedium_Handle_SendsLinkAndRecords`. **Caveat**: `telegram.InlineKeyboardButton` (internal/telegram/types.go) only supports `callback_data`, not a Telegram `url` button — adding that button type would mean editing `internal/telegram`, out of this ticket's `touches` (internal/blog/medium.go only). So the link ships as auto-linkified plain message text (still one-tap in any Telegram client), not a distinct inline button; documented in medium.go's `TelegramSender` doc comment. **Dashboard surfacing is not implemented here** — this ticket only emits the `blog.medium_link_sent` event + sets `content_items.stage`; wiring that onto a dashboard content-detail view is an `internal/httpapi`/web concern outside `touches`, left for whichever ticket builds that view. Flagging explicitly so it isn't silently dropped.
- [x] This step is **not** routed through `approval.request`/D5 the way a publish is — nothing is actually published here; the only "publish" is Mayank clicking through and completing Medium's own import UI himself. State this distinction explicitly in the code/comments and in the dashboard copy, rather than presenting it as an automated publish. Proven: `medium.go` never imports `internal/content` and never calls `approval.request`/`RequireApproved`; the package doc comment, `Handle`'s doc comment, and the Telegram message text itself (`importMessageText`) all state explicitly this is a manual step, not an automated publish. (No dashboard copy exists yet since dashboard surfacing is out of `touches` — see above.)
- [x] Does not create a `publications` row with a fabricated `external_id`/`url` implying an automated Medium publish happened. If the daemon needs to track "import link sent," use an `events` row or a `content_items` status (e.g. `medium_link_sent`) instead — never a row that reads like a real publish. Proven: `medium.go` has zero `INSERT`/`UPDATE` statements against `publications` (only a `SELECT`); uses `content_items.stage = "medium_link_sent"` (`stageMediumLinkSent`) plus an `events` row (`EventMediumLinkSent = "blog.medium_link_sent"`) — both asserted in `TestMedium_Handle_SendsLinkAndRecords`.
- [x] Idempotent: re-running for an already-sent link does not spam Mayank a second Telegram message; if re-sending on request is desired, it's gated behind an explicit re-request, not automatic re-trigger. Proven by `TestMedium_Handle_IdempotentNoDuplicateSend` (calls `Handle` 3x for the same content_id; fake sender's call count stays at 1 after the first run). `Handle` has no "force resend" parameter — a real re-request would need a caller to reset `content_items.stage` explicitly first; it cannot happen implicitly from an at-least-once retry/redelivery.
- [x] Table-driven tests cover: import-link construction from a given canonical URL, Telegram message dispatch (fake bot), and idempotent no-duplicate-send. `TestBuildImportURL` (table-driven, 9 cases), `TestMedium_Handle_SendsLinkAndRecords` (fake `TelegramSender`, no real network), `TestMedium_Handle_IdempotentNoDuplicateSend`. Plus extra coverage beyond the minimum: bad payload, missing/unknown content_id, publication-not-yet-live (retryable vs. permanent error distinction), Telegram send failure (must not mark sent), nil sender, `RegisterHandler` wiring.
