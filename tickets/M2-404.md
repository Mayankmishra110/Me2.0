## Goal
Per CONTEXT D19 (Medium has no usable publishing API), package the canonical Mayankbuilt post into whatever Medium's "Import a story" flow needs and deliver it as a one-tap link via Telegram/dashboard. Mayank completes the import himself in Medium's own UI — this ticket does **not** publish to Medium.

## Acceptance criteria
- [ ] `internal/blog/medium.go` implements the Medium leg triggered after M2-401's `blog.merge` succeeds: reads the now-live canonical post's public URL from `publications` (`platform = "mayankbuilt"`).
- [ ] Builds Medium's "Import a story" URL from that public URL (Medium's import flow historically accepts the source article URL as a query parameter — exact current parameter name/path not fully certain, see Notes). No OAuth, no API call, no token of any kind is used, since none exists (D19).
- [ ] Sends the import link to Mayank via Telegram (a message with an inline button/link, same delivery mechanism as approval prompts) and surfaces it on the dashboard (e.g. alongside the content detail view for that post).
- [ ] This step is **not** routed through `approval.request`/D5 the way a publish is — nothing is actually published here; the only "publish" is Mayank clicking through and completing Medium's own import UI himself. State this distinction explicitly in the code/comments and in the dashboard copy, rather than presenting it as an automated publish.
- [ ] Does not create a `publications` row with a fabricated `external_id`/`url` implying an automated Medium publish happened. If the daemon needs to track "import link sent," use an `events` row or a `content_items` status (e.g. `medium_link_sent`) instead — never a row that reads like a real publish.
- [ ] Idempotent: re-running for an already-sent link does not spam Mayank a second Telegram message; if re-sending on request is desired, it's gated behind an explicit re-request, not automatic re-trigger.
- [ ] Table-driven tests cover: import-link construction from a given canonical URL, Telegram message dispatch (fake bot), and idempotent no-duplicate-send.

## Notes
- **This is not a full API publish and must not be presented to Mayank or on the dashboard as one.** Medium stopped issuing integration tokens (D19); this ticket only prepares and delivers a link. The actual "publish to Medium" step is a manual action Mayank takes himself.
- Not fully certain of Medium's current import-URL parameter shape (`medium.com/p/import?url=...` is the historically known pattern for Medium's "Import a story" feature, but Medium has changed its import-flow URLs before and may require the user to already be logged in, or may not accept a bare query parameter anymore). **Verify against Medium's actual current site before implementing** — don't build this from memory of an old pattern.
- ARCHITECTURE §3.2's flow diagram draws the Medium step as a fourth branch off the same approval point as LinkedIn/X, but SPEC §5's job-type list only has one generic `blog.repurpose` type covering all repurpose destinations — it isn't fully specified whether Medium should be a `blog.repurpose` destination case or its own trigger directly off `blog.merge`. Either wiring satisfies the acceptance criteria above; pick whichever is simplest and document the choice made.
- Whether Mayankbuilt's repo structure/MDX conventions are documented anywhere for reuse here: no, same gap noted in M2-401 — this ticket only needs the already-published public URL, not the MDX source, so it isn't blocked by that gap, but confirm the URL format (e.g. does the live post live at `mayankbuilt.com/blog/<slug>` or something else) before hardcoding any URL construction.
