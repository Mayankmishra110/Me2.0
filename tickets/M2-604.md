## Goal
Board/pin strategy for affiliate links (Amazon, software affiliate programs — CONTEXT §2 line 4: "Pinterest + affiliate → Amazon and software affiliate income"), producing Idea/video pins through the Pinterest publisher already built in M2-304 (P3, `status: done`, `internal/publish/pinterest.go`). This ticket is the content-selection/strategy layer that feeds M2-304, not a second Pinterest publisher — M2-304 already owns `Publisher.Publish`, board posting, the affiliate-disclosure-in-description requirement, and the explicit no-link-cloaking rule; this ticket must not duplicate or relax any of that.

## Acceptance criteria
- [x] A board/pin content-selection step (package/location TBD by the implementer — likely a new stage in `internal/content/` alongside the existing scout→research→script pipeline, since Pinterest pins here are a distinct content type: product-and-affiliate-link driven rather than script/video driven) that picks or generates: a target product/affiliate link (Amazon Associates or a software affiliate program per CONTEXT §2), a board to pin to, and pin copy (title + description).
- [x] Reuses `internal/llm` for pin copy generation — route under the existing `script` or `metadata` task (free-tier chain), not Claude, for the same CLAUDE.md reason as M2-603 ("Claude is for Builder and blog only" — Pinterest pin copy is content-agent output, not Builder or blog).
- [x] Every affiliate pin's description includes the FTC-required affiliate disclosure (COMPLIANCE §1 "US FTC | Endorsement guides | Clear affiliate disclosure in descriptions and captions") — this ticket generates that disclosure text as part of the pin copy it hands to M2-304, it does not re-implement M2-304's own disclosure-presence check (M2-304's AC already requires the description carry the disclosure "when the pin is affiliate-linked").
- [x] **No link-cloaking, matching M2-304's existing non-negotiable exactly** — this ticket must produce and hand off a plain outbound affiliate URL (e.g. a standard Amazon Associates tagged URL), never a shortened/cloaked/redirect-through-our-own-domain link. Do not relax or work around M2-304's "plain outbound URL" requirement by, say, routing links through an internal redirect endpoint for click tracking — if click analytics on affiliate links are wanted later, that needs its own explicit decision (flag to CONTEXT.md if it comes up), not a quiet reinterpretation here.
- [x] Respects Pinterest's caps and the "one pin per destination link per day max" rule (COMPLIANCE §3/§4, already enforced as a fail-closed check inside M2-304's `Publish`) — this ticket's selection step should not even attempt to schedule a second same-day pin to a destination already used that day; treat M2-304's rejection as a backstop, not the primary control.
- [x] Goes through the same approval flow as every other publish path (D5, F7) before `publish.pinterest` fires — this ticket's output is a pin candidate that becomes a normal `content_items`/`approval.request` flow, reusing the existing render/approval machinery rather than inventing a Pinterest-only approval shortcut.

CONTEXT §6's external-accounts checklist — this ticket should add a line there if it introduces new setup steps, e.g. "Amazon Associates account" / "Pinterest board(s) created for affiliate content").
- [x] Table-driven tests: pin-copy generation includes disclosure text when a link is affiliate, never routes to Claude (assert provider list), no-link-cloaking (destination URL passed through unmodified, not rewritten to an internal redirect), duplicate-destination-same-day is not even attempted (selection step skips it independent of M2-304's own check), approval-request created before any `publish.pinterest` call.

## Notes
- **Scope boundary, stated plainly:** M2-304 (already `ready`, phase 3) is the Pinterest `Publisher` — API calls, idempotency, board posting, the disclosure-presence check, the cap/duplicate-destination check, token handling. This ticket (M2-604, phase 6) is upstream of it: deciding *what* to pin and *what the copy says*. Keep that boundary; if this ticket's implementer finds themselves editing `internal/publish/pinterest.go`, that's a sign the work belongs in M2-304's follow-up, not here — coordinate rather than duplicating logic that already exists (or silently changing M2-304's non-negotiables).
- **Flagged, not asserted:** exactly where the board/pin selection logic should live (`internal/content/` alongside the video pipeline vs. a new small package, e.g. `internal/affiliate/`) is genuinely a judgment call — `touches` above lists `internal/content/` as the default guess but the implementer should confirm this doesn't collide with in-progress work on the video content pipeline (P2 tickets) before claiming overlapping paths, per SPEC §2's "if you must touch another ticket's in-progress paths, stop and note it" rule.
- Affiliate income itself (clicks converting to Amazon/software-affiliate commission) isn't observable by this system at all — Amazon/most affiliate programs don't expose a real-time API this daemon can poll for commission earned. This ticket's contribution to revenue is entries staying **manual** in `internal/revenue` (M2-601) — Mayank periodically checks his Amazon Associates / affiliate dashboards and enters the numbers. Do not build a scraper against an affiliate dashboard to "automate" this — that would cross CLAUDE.md's "no scraping behind logins" line. Flag this limitation on the Revenue screen copy itself if useful (e.g. "affiliate income is entered manually") rather than implying it's live-tracked.
- `depends: [M2-304, M2-601]` per this batch's brief: M2-304 because this ticket's pins are meaningless without the publisher that actually posts them; M2-601 because affiliate income ultimately lands there as a manual entry (see above).
