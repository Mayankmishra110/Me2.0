## Notes
- **`/api/agents` derivation (technical decision, not a product question —
  BOOT.md §3: decided and recorded here rather than asked of Mayank):**
  `httpapi.Server` only holds the queue through the narrow `Pauser` interface
  (pause/resume), not `*queue.Queue` itself, so this handler cannot introspect
  the live `Register`-ed handler map without widening that interface and
  touching `internal/queue`/`cmd/mayank2` wiring outside this ticket's
  `touches`. Instead the agent roster (id, display name, job types) is a
  fixed table taken directly from DESIGN.md's named agent-card list and
  SPEC.md §5's job-type list — not invented — and every field on each card
  (`state`, `currentJob`, `lastSuccess`, `nextRun`) is computed with real
  queries against the `jobs` table (plus `pause:all` / `pause:agent:<id>`
  settings) for that agent's job types. `nextRun` reflects the next *already
  queued* row's `run_at` for that type, not a recomputation of the
  scheduler's cron spec (`internal/scheduler`'s trigger times are
  unexported and only 4 of the ~17 agents are cron-driven at all) — so
  cron-only agents (Scout, Analytics, and the scheduler's own daily-summary/
  cleanup jobs) correctly show `nextRun: null` between the moment a cron
  job finishes and the moment the next one is actually enqueued, rather than
  a guessed timestamp. This is the "most conservative, clearly-real subset"
  fallback the finding allowed; wiring a real `*queue.Queue` + `*scheduler.Scheduler`
  reference into `httpapi.Server` for a fuller `nextRun` is a good follow-up
  ticket, not done here to stay inside `touches`.
- `builder.plan`/`builder.implement`/`builder.gate` are grouped under
  "Builder Implementer" and `builder.audit` under "Builder Auditor" (DESIGN.md
  names only those two Builder cards; SPEC §5 has four Builder job types).
- Topics: both `GET` and `POST /api/topics` now use `channelId`/`sourceUrl`,
  matching the camelCase convention already used by every other multi-word
  JSON field in `internal/httpapi` (e.g. `channelId` in
  `GET /api/channels/{id}/metrics`, `GET /api/topics` itself). No web client
  code referenced the old snake_case request shape (checked
  `web/src/api/types.ts`, `web/src/api/hooks.ts` — topics has no typed client
  yet, only the MSW mock in `web/src/mocks/handlers.ts`, updated to match).
