## Goal
Same repurpose pattern as M2-402 but for Mayank's **personal** X account: a thread version of the canonical post, published via X API v2 once approved (D5). Must never share credentials, tokens, or account plumbing with the **business** X account publisher (M2-303) — COMPLIANCE §1 and CONTEXT D12 draw this line explicitly and it must stay hard in code, not just in policy.

## Acceptance criteria
- [x] `internal/blog/repurpose_x.go`: input is the live Mayankbuilt post; calls `internal/llm.Complete(ctx, "blog", req)` to produce an X thread (multiple tweet-length posts, each under X's character limit — truncate/reject at a word boundary per format rules, never cut mid-word, same discipline as M2-303) with its own hook tweet, not a copy-paste of the blog intro.
  Proof: `XRepurposer.repurpose` calls `Completer.Complete(ctx, llm.TaskBlog, ...)` with a JSON-schema-constrained request; `normalizeThread`/`enforceTweetLength`/`looksCopyPasted` enforce the limit and the not-copy-paste rule. Tests: `TestXRepurposer_StartHappyPath`, `TestXRepurposer_RejectsCopyPastedHook`, `TestEnforceTweetLength` (word-boundary truncation + reject-when-no-boundary), `TestNormalizeThread_*`, `TestLooksCopyPasted`.
- [x] Creates an `approval.request` (`content_items.kind = "blog"`, platform `"x_personal"`) with the full thread text and source link; Reject/Redo(note) re-runs the repurpose step with the note.
  Proof: `XRepurposer.Start`/`Redo` insert a `content_items` row (`kind='blog'`, `format='x_thread'`) and call `content.ApprovalService.Start` (via the narrow `ApprovalStarter` interface) which enqueues `approval.request`. Tests: `TestXRepurposer_StartHappyPath`, `TestXRepurposer_Redo`.
- [x] `internal/publish/x_personal.go` implements `Publisher`: `Platform()` returns `"x_personal"` — a distinct platform string from M2-303's `"x"` (business), so `publications` rows and idempotency keys never collide between the two accounts.
  Proof: `PlatformXPersonal = "x_personal"`; `XPersonal.Platform()` returns it. `publications.idempotency_key` in tests is `content_id:x_personal:account`, structurally distinct from any `...:x:...` key M2-303 would use.
- [x] **Hard requirement, checked in code review and by test**: `x_personal.go` must not read, import, or reference the business publisher's `account_ref`, token, or any shared default — it resolves its own personal-account credentials from `internal/secrets` by its own distinct `account_ref` string. Add a test asserting the personal publisher's token-lookup key differs from the business publisher's and that no shared constant/default exists between `internal/publish/x.go` and `internal/publish/x_personal.go`.
  Proof: `x_personal.go` never imports/references `x.go` (which doesn't exist yet — see Notes). `SecretsPlatform = "x_personal"` (a distinct `internal/secrets` platform key, not just a distinct account under the business platform key) and `DefaultAccountRef = "mayank_x_personal"`. Tests: `TestXPersonal_CredentialIsolation` (fake token store, asserts the exact `(platform, account)` pair requested is never the business one) and `TestXPersonal_CredentialIsolation_RealSecretsStore` (same proof against the real `internal/secrets.Store`, DPAPI-backed, storing both a representative business token and the personal token and confirming they never collide/never return each other).
- [x] Refuses to call the API unless the item's `approvals` row is `status = approved` (D5, F7).
  Proof: `Publish` calls `content.RequireApproved` first. Test: `TestXPersonal_RequiresApproval`.
- [x] Posts the thread via `POST /2/tweets` per tweet with reply-chaining for the thread, idempotent on `p.IdempotencyKey` — a repeat call must not re-post a partial thread.
  Chose **partial-thread recovery**: posted tweet IDs are persisted progressively into `publications.external_id` as a JSON array while `status='publishing'`; a retry resumes posting from `len(posted)` rather than tweet 0, chaining `in_reply_to_tweet_id` off the last stored id. On completion `external_id` is overwritten with the plain root tweet ID and `status='published'`, which also gives full-replay-is-a-no-op for free (status check short-circuits before any posting). Tests: `TestXPersonal_PublishHappyPath` (reply-chain correctness), `TestXPersonal_Idempotent` (full replay no-op), `TestXPersonal_PartialThreadRecovery` (resumes from tweet 2/3, does not repost tweet 1, does not double-charge the daily cap).
- [x] Respects the X personal daily cap (≤ 3 posts/day, COMPLIANCE §4) — fails closed rather than posting past it. Treats one thread as one post against the cap (assumption, see Notes).
  Proof: `reserveDailyCap` (same atomic `quotas` upsert pattern as `internal/publish/youtube.go`'s `reserveQuota`), reserved once per thread (only when `len(posted)==0`, so a mid-thread retry doesn't double-charge). Test: `TestXPersonal_CapExceeded` (fails closed, publication marked `failed`, zero API calls).
- [x] On success, records `external_id` (thread's root tweet ID) and `url` in `publications`; on failure, wraps errors with `%w`, error detail (not the token) in `error` (schema column name; ticket says "last_error").
  Proof: `completePublication`/`failPublication`. `HTTPXPersonalAPI` uses the same `redact()` helper `youtube.go` already defines in this package to strip bearer-shaped substrings from API error bodies. Test: `TestXPersonal_HTTPAPI_ErrorRedactsBody`.
- [x] Table-driven / behavioral tests cover: repurposed text differs from source, thread-chaining idempotent replay (including partial-thread recovery), missing approval, over-length tweet handling, cap exceeded, the credential-isolation test above, and a happy-path publish against a fake X API server (`httptest`).
  Proof: see `internal/blog/repurpose_x_test.go` and `internal/publish/x_personal_test.go`. The interface-level fake (`fakeXAPI`) covers the business-logic tests, matching `internal/publish/youtube_test.go`'s established pattern; `TestXPersonal_HTTPAPI_HappyPath`/`TestXPersonal_HTTPAPI_ErrorRedactsBody` additionally exercise the real `HTTPXPersonalAPI` HTTP client against a genuine `httptest.NewServer`, which `youtube_test.go` does not do for `HTTPYouTubeAPI` — added here to satisfy the ticket's literal "(httptest)" wording.

## Notes

### Plan (written before coding, per _engineer.md)
Files: `internal/blog/repurpose_x.go` (LLM repurpose + content_items + approval.request), `internal/publish/x_personal.go` (Publisher). Interfaces: local `Completer`/`ApprovalStarter` (mirrors `internal/content.Completer`) so both files are testable without a real router/DB-coupled ApprovalService. Test cases: see acceptance criteria above. Risk: `internal/content.ApprovalService` (M2-210, not in my touches) turned out to have two assumptions that don't fit blog content — see "Architecture gaps hit" below; worked around them inside my own touches rather than editing approval.go.

### M2-303 status at implementation time
`git branch -a | grep M2-303` showed `m2/M2-303` exists, but `git diff phase/p1-foundation m2/M2-303 --stat` was empty and `git log m2/M2-303 -5` showed no commits beyond the shared `phase/p1-foundation` base — **M2-303 has not been built yet**. There was no `internal/publish/x.go` to read. Per the task instructions for this situation, I used an obviously distinct naming convention myself:
- `internal/publish/x_personal.go`'s `Platform()` returns `"x_personal"` (ticket-specified, distinct from `"x"`).
- Its `internal/secrets` credential key is a **distinct platform string**, `SecretsPlatform = "x_personal"` — not merely a distinct account under a shared `"x"` platform key. Since `oauth_tokens` is keyed `PRIMARY KEY (platform, account)`, this means the two publishers' tokens can never collide even if M2-303 later picks a careless/default `account_ref` under platform `"x"`.
- Default account ref `DefaultAccountRef = "mayank_x_personal"` (unmistakably not `"business"`/`"default"`/`"x-business"`).
- `TestXPersonal_CredentialIsolation` and `TestXPersonal_CredentialIsolation_RealSecretsStore` encode a **representative** business key (`platform="x"`, `account="business"`, clearly commented as this ticket's own assumption of M2-303's convention, not a read of real code) and assert the personal publisher's resolved key is never that pair, never falls back to it, and (in the second test) that two real `internal/secrets.Store` tokens stored under both keys never collide or read back as equal.
- **Action for whoever lands/merges M2-303**: re-diff `internal/publish/x.go`'s actual `Platform()`/account_ref/secrets-platform convention against these constants once it exists, to confirm the structural non-collision holds for real (it will, by construction, as long as M2-303 also doesn't invent a platform key literally equal to `"x_personal"`).

### Architecture gaps hit (decided, not guessed — technical, not product, calls)
1. **`content.ApprovalService.Decide`'s redo branch hardcodes `content.JobScriptWrite` ("script.write")** regardless of `content_items.kind`. That's correct for video content but wrong for blog repurposes (M2-401's own ticket text says redo should re-run `blog.draft`, not `script.write` — same mismatch, not unique to this ticket). Since `internal/content/approval.go` is outside this ticket's `touches`, I did not edit it. Instead, `XRepurposer.Redo` implements its own redo path (re-run the LLM once, update the existing `content_items` row, open a **new** `approvals` row via `ApprovalStarter.Start`) and does not call `ApprovalService.Decide` at all for the redo step.
2. **Wiring "who calls `XRepurposer.Redo` with the human's note"** (i.e. how a Telegram/dashboard Reject/Redo tap on a `kind='blog'` approval routes to this repurposer instead of the generic video redo path) is not in this ticket's touches and isn't built anywhere yet. Flagged as a follow-up integration point — likely belongs to whichever ticket generalizes `ApprovalService` for blog content, or a small `kind`-based dispatch in the decision HTTP handler.
3. **`PublishRequest` (owned by `internal/publish/youtube.go`, M2-211, outside my touches) has no thread/array field.** `x_personal.go` encodes the thread as a JSON array of strings in `PublishRequest.Description` (documented in code). Flagged for a follow-up once more text-thread publishers exist (M2-402 LinkedIn only needs one string, so this is X-specific) to add a proper typed field.
4. **SPEC §5's job list has only `publish.x` and a single shared `blog.repurpose`**, with no platform-dispatch mechanism and no shared dispatcher built yet. Registering handlers under those exact shared names from a solo ticket would collide with the sibling M2-402/404 tickets building in parallel worktrees. I used my own platform-qualified job type names (`blog.repurpose_x_personal`, `publish.x_personal`) as constants for future wiring, without actually calling `queue.Register` for either (no queue wiring was in this ticket's acceptance criteria; the content_items→PublishRequest translation glue is also not built yet). Flagged for a follow-up SPEC/dispatcher update.
5. `content_items.channel_id` is `NOT NULL REFERENCES channels(id)`. There is no seeded "blog" channel row anywhere in this repo yet. `XRepurposer.ChannelID` defaults to `"blog"`; tests seed that row themselves. A real seed (config/channels or a migration) is assumed to land via M2-401 or a shared blog-pipeline ticket — not created here.

### Assumptions carried over from the ticket text (unchanged, still open)
- "1 thread = 1 post" against the ≤3/day X-personal cap (COMPLIANCE §4) — implemented as such; flag to Mayank if wrong.
- X API v2 auth requirements (OAuth 1.0a vs 2.0 user-context) and whether the personal account needs a fully separate developer-app registration from the business one — **not re-verified against live X docs in this pass** (no network access in this environment); the code is written against `POST /2/tweets` with a Bearer access token, which is the stable, well-documented v2 shape for text-only tweet creation regardless of that outcome. Flagged under CONTEXT §5 Open questions is warranted if this is decided at wiring time.

### Deviation from ticket wording
"last_error" in the acceptance criteria refers to the schema's `publications.error` column (confirmed via `migrations/001_init.sql`; there is no separate `last_error` column) — used `error` throughout, matching `youtube.go`'s existing convention.
