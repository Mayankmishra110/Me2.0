## Goal
Same repurpose pattern as M2-402 but for Mayank's **personal** X account: a thread version of the canonical post, published via X API v2 once approved (D5). Must never share credentials, tokens, or account plumbing with the **business** X account publisher (M2-303) — COMPLIANCE §1 and CONTEXT D12 draw this line explicitly and it must stay hard in code, not just in policy.

## Acceptance criteria
- [ ] `internal/blog/repurpose_x.go`: input is the live Mayankbuilt post; calls `internal/llm.Complete(ctx, "blog", req)` to produce an X thread (multiple tweet-length posts, each under X's character limit — truncate/reject at a word boundary per format rules, never cut mid-word, same discipline as M2-303) with its own hook tweet, not a copy-paste of the blog intro.
- [ ] Creates an `approval.request` (`content_items.kind = "blog"`, platform `"x_personal"`) with the full thread text and source link; Reject/Redo(note) re-runs the repurpose step with the note.
- [ ] `internal/publish/x_personal.go` implements `Publisher`: `Platform()` returns `"x_personal"` — a distinct platform string from M2-303's `"x"` (business), so `publications` rows and idempotency keys never collide between the two accounts.
- [ ] **Hard requirement, checked in code review and by test**: `x_personal.go` must not read, import, or reference the business publisher's `account_ref`, token, or any shared default — it resolves its own personal-account credentials from `internal/secrets` by its own distinct `account_ref` string. Add a test asserting the personal publisher's token-lookup key differs from the business publisher's and that no shared constant/default exists between `internal/publish/x.go` and `internal/publish/x_personal.go` (COMPLIANCE §1 X row: business and personal X accounts never share posts or credentials; CONTEXT D12).
- [ ] Refuses to call the API unless the item's `approvals` row is `status = approved` (D5, F7).
- [ ] Posts the thread via `POST /2/tweets` per tweet with reply-chaining for the thread, idempotent on `p.IdempotencyKey` — a repeat call must not re-post a partial thread: either the full set of posted tweet IDs is recorded and replay is a no-op, or partial-thread recovery resumes from the last successfully posted tweet rather than reposting from the start. Pick one approach and test it.
- [ ] Respects the X personal daily cap (≤ 3 posts/day, COMPLIANCE §4) — fails closed rather than posting past it. Treats one thread as one post against the cap unless told otherwise (flagged as an assumption below).
- [ ] On success, records `external_id` (thread's root tweet ID) and `url` in `publications`; on failure, wraps errors with `%w`, error detail (not the token) in `last_error`.
- [ ] Table-driven tests cover: repurposed text differs from source, thread-chaining idempotent replay (including partial-thread recovery), missing approval, over-length tweet handling, cap exceeded, the credential-isolation test above, and a happy-path publish against a fake X API server (`httptest`).
