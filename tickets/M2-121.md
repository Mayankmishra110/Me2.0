## Goal
M2-117 wired `blog.draft`/`blog.merge`/`blog.repurpose` into `cmd/mayank2/run.go` and left `blog.medium`
(M2-404, `internal/blog/medium.go`) as the one remaining SPEC §5 job type still unregistered, because
`medium.go`'s `TelegramSender` needs a way to send a Telegram message and `internal/telegram.Bot` exposed
no public surface to do that (CONTEXT open question 6). Wire `blog.medium` end to end: register it in the
daemon, chain `blog.merge` into it the same way it already chains into `blog.repurpose`, and give
`internal/telegram.Bot` the minimal accessor `blog.medium` needs.

## Acceptance criteria
- [x] `internal/telegram.Bot` gets a narrow accessor blog.medium can use to send Mayank a message — not a
      wholesale `Bot.Client()`. Added `Bot.SendMessage(ctx, chatID, text, markup) (int64, error)` (matches
      `blog.TelegramSender`'s interface exactly, so `*telegram.Bot` satisfies it directly) and
      `Bot.ChatID() int64`. Both are read-only/send-only: no polling, no allowlist bypass, no shared
      mutable state beyond the existing `*Client`.
- [x] `blog.merge`'s `Run` (`internal/blog/merge.go`) enqueues `blog.medium` (via the existing
      `MergeOptions.Enqueue`) right after its existing `blog.repurpose` enqueue, on a genuinely new merge
      only — same idempotency guard as `blog.repurpose` (the early `lookupPublished` return on an
      already-merged `content_id` means neither enqueue call is ever reached on a replay). A failed enqueue
      is logged and swallowed (non-fatal), matching the `blog.repurpose` call right above it.
- [x] `cmd/mayank2/run.go` registers `blog.medium` (`registerBlogHandlers`), gated the same way as
      `blog.draft`/`blog.merge`/`blog.repurpose`: only when `cfg.Blog.Enabled()` (D24). Does not crash or
      block startup when Telegram is disabled (`TELEGRAM_BOT_TOKEN` unset, `bot == nil`) — `blog.medium`
      still registers with a nil `Sender` in that case (same "registered, fails cleanly at use time" shape
      as `visuals.fetch` with no stock provider key), rather than being left unregistered and making
      `blog.merge`'s non-fatal enqueue-failure log the only signal.
- [x] `TestRunDaemon_everySpecJobTypeRegistered` (`cmd/mayank2/run_test.go`) covers `blog.medium` (added to
      `specJobTypes`, doc comment updated to explain it isn't in SPEC §5's own literal list yet — see
      Notes).
- [x] New tests: `TestMerge_RunChainsRepurposeAndMedium` (blog.merge chains both jobs once, not again on
      replay), `TestBot_SendMessage` / `TestBot_ChatID` / `TestBot_SendMessage_NilBot` (telegram accessor).
- [x] CONTEXT.md open question 6 closed with a decision-log row; the pre-existing duplicate-numbering bug
      in CONTEXT §5 (two "5"s, two "6"s, two "7"s — flagged out-of-scope by a prior reviewer) cleaned up in
      the same edit since this ticket is already touching that section.

## Notes

### Decision: accessor on `internal/telegram.Bot`, not a second Telegram client (2026-09-29, crew-be)

Verified before committing to the recommendation in the open question, per instruction:

- `internal/blog/medium.go`'s `TelegramSender` interface needs exactly one method:
  `SendMessage(ctx, chatID, text, markup) (int64, error)`. No state, no polling, no callback handling —
  medium.go already deliberately avoids buttons (`InlineKeyboardButton` only supports `callback_data`, not
  a `url` button) and just sends plain text Telegram auto-linkifies.
- `internal/telegram/bot.go`'s `Bot` wraps an unexported `*Client` (`internal/telegram/client.go`).
  `Client`'s full method set is `GetUpdates`, `SendMessage`, `SendPhoto`, `SendVideo`, `EditMessageText`,
  `EditMessageCaption`, `AnswerCallbackQuery` — no allowlist/PIN/nonce logic lives in `Client` at all; every
  bit of that lives in `Bot` (`Bot.handleMessage`'s `allowed()` check, `Bot.awaitingPIN`/`awaitingRedo`,
  `Bot.Run`'s own long-poll loop and stored `settings.telegram:offset`).
- **A literal `Bot.Client()` accessor (what the open question's text proposed as one option) would have
  been unsafe**: it would also hand out `Client.GetUpdates`. A second caller polling `GetUpdates`
  concurrently with `Bot.Run`'s own long-poll loop could steal/skip inbound updates out from under it —
  Telegram's `getUpdates` offset semantics mean whichever caller processes an update first advances past it
  for both. That would mean approval button taps or `/pause`/`/resume` commands silently going missing,
  entirely bypassing `Bot.handleMessage`'s allowlist check (which only runs on updates `Bot.Run` itself
  receives) — a real regression of the control surface CLAUDE.md/D5 depend on, for a feature (`blog.medium`)
  that only ever needs to *send*, never *receive*.
- So: **added `Bot.SendMessage` and `Bot.ChatID` directly on `Bot`** (delegating to the same unexported
  `*Client`), not a `Bot.Client()` accessor and not a second Telegram client built inside
  `internal/blog/medium.go`. This is narrower than what the open question literally proposed
  (`Bot.Client()`) but keeps the question's actual reasoning intact: one token, one HTTP client, one place
  future rate-limit/retry logic would live, per CLAUDE.md's "Telegram bot" (M2-105) being the one place
  Telegram access should live. `Bot.SendMessage`'s signature matches `blog.TelegramSender` exactly, so
  `*telegram.Bot` satisfies that interface with no adapter type needed.

### Wiring order in cmd/mayank2/run.go

`buildTelegramBot` was previously called after `queue.StartWorkers` (line ~249 pre-change), but
`registerBlogHandlers` (which now needs the bot to build `blog.Medium`'s `Sender`) runs before
`StartWorkers`, per the existing "every real job handler is registered exactly once, from here, before
StartWorkers runs" rule (`queue.Queue.Register`'s own doc comment: "not safe to call concurrently with
Enqueue/StartWorkers"). Moved *construction* of the bot earlier (right before the registration block);
`bot.RegisterHandlers(q)` (owns `approval.request`) and the `bot.Run(ctx)` goroutine stay where they were,
after `StartWorkers` — only reused the same `bot` variable. Did not touch the pre-existing
`bot.RegisterHandlers(q)` call site itself or its own ordering relative to `StartWorkers`; that's a
separate, pre-existing question outside this ticket's `touches`.

### blog.medium not in SPEC §5's literal job-type list

`docs/SPEC.md` §5 still doesn't enumerate `blog.medium` (only `blog.draft`, `blog.merge`,
`blog.repurpose`) — `internal/blog/medium.go`'s own doc comment on `JobBlogMedium` already flagged this as
predating the ticket. Left SPEC §5's list as-is (out of this ticket's product-decision scope to silently
add a new job type to the canonical list) but the daemon-level test
(`TestRunDaemon_everySpecJobTypeRegistered`) now separately covers `blog.medium` since it's a real,
registered job type regardless of SPEC §5's text.

### `needs-sec: yes`

Touches `internal/telegram/bot.go` (adds a new public surface on the Telegram control-plane type) and the
Telegram-adjacent send path for `blog.medium`. No new secrets, no new external call surface beyond what
