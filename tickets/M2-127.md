## Goal

`mayank2 set-pin` actually sets a PIN (bcrypt hash persisted to `settings.pin_hash`), and
`POST /api/resume`'s `checkPIN` fails closed: no PIN configured means resume is refused, not
silently allowed through on any non-empty string.

## Background (live E2E audit finding)

- `cmd/mayank2/main.go` routed `set-pin` to `cmdStub`, which prints "not implemented yet" and
  returns success (exit 0) without touching the database.
- `internal/httpapi/routes.go`'s `checkPIN` (pre-fix) read `settings.pin_hash`; if no row existed
  (which was always true, since nothing ever wrote one), it fell back to "any non-empty string is
  accepted". Confirmed live: `POST /api/resume {"scope":"all","pin":"0000"}` succeeded.
- Net effect: SPEC §4 ("resume needs PIN") and ARCHITECTURE.md's "PIN-gated resume" were not
  enforced at all — the HTTP resume path had no real PIN gate since `set-pin` never ran.
- `internal/telegram` already had the right shape for this (`HashPIN`, `SetPINHash`,
  `settingPINHash = "pin_hash"`, bcrypt compare in `completePIN`) — the CLI and HTTP paths just
  never wired up to match it.

## Acceptance criteria

- [x] `mayank2 set-pin` prompts for a PIN on a real terminal with echo suppressed
      (`golang.org/x/term.ReadPassword`); when stdin is not a terminal (piped/tests), it reads a
      line from stdin instead. No PIN is ever accepted as a bare CLI argument (would land in shell
      history / process list / `ps`).
- [x] The PIN is confirmed (entered twice, must match) when read interactively.
- [x] `set-pin` hashes with `golang.org/x/crypto/bcrypt` (`bcrypt.DefaultCost`) and writes the hash
      to `settings` under key `pin_hash` via the same upsert pattern every other setting uses
      (`INSERT ... ON CONFLICT(key) DO UPDATE`).
- [x] `checkPIN` in `internal/httpapi/routes.go` now fails closed: no `pin_hash` row (or empty
      value) → resume is refused unconditionally, regardless of what PIN string is supplied. A PIN
      is only ever accepted via `bcrypt.CompareHashAndPassword` against a real stored hash.
- [x] Nothing logs the raw PIN anywhere (grepped `internal/httpapi`, `cmd/mayank2`, `internal/telegram`
      for PIN-adjacent log lines — only hashes or generic messages are logged, matching the existing
      telegram PIN code's comment "The raw PIN is never logged").
- [x] Tests: `set-pin` persists a real bcrypt hash (not plaintext) to `settings`; `checkPIN` accepts
      the correct PIN, rejects a wrong PIN, and rejects every PIN (including empty) when no hash is
      set yet.

## Notes

**PIN-entry mechanism chosen: masked stdin prompt via `golang.org/x/term`, not a CLI argument.**
`golang.org/x/term` was not yet a direct dependency (`x/crypto`, `x/oauth2`, `x/sys` already are,
same `golang.org/x` family); added it rather than taking the PIN as `os.Args`, because an argv PIN
is readable from shell history and from any other process on the box via the process list — a
materially worse exposure than an unlisted dependency. `term.ReadPassword(fd)` is used only when
`term.IsTerminal(fd)` is true; non-interactive stdin (CI, tests, piping a PIN in) falls back to a
plain line read via `bufio.Reader`, so `set-pin` stays scriptable without ever taking the PIN as an
argument.

**No DPAPI wrapping for `pin_hash`.** `internal/secrets` DPAPI-wraps OAuth tokens because those are
reversible bearer credentials — if stolen, they can impersonate the account directly. A bcrypt hash
is already one-way and salted; wrapping it in DPAPI would only protect against an attacker who can
read the SQLite file but not call Windows crypto APIs, which is not a scenario in this threat model
(both live on the same user profile), and would complicate every future `checkPIN`/`set-pin` call
for no real gain. Storing the bcrypt hash directly in `settings`, exactly as `ARCHITECTURE.md`
already specified ("PIN hash (bcrypt)" in the `settings` row), is correct and matches what
`internal/telegram` already does.

**Fail-closed semantics.** Before this ticket, no `pin_hash` meant any non-empty string unlocked
resume — the opposite of fail-closed. Now no `pin_hash` means resume is unconditionally refused
until `set-pin` has been run once. This is a deliberate behavior change: a fresh install can no
longer resume a paused queue over HTTP without first setting a PIN via the CLI. Telegram's bot
already enforced this correctly (`completePIN`: `if hash == "" { ... "PIN not configured" }`);
HTTP now matches.
