## Goal
`builder.gate` job that runs after each `builder.audit` completes and decides whether the plan may proceed to the next subphase, or whether the audit's findings must go back to the Implementer as a fix-and-retry loop (bounded by `config.builder.max_fix_attempts`, already in `config.example.yaml`). Also owns the cross-cutting timeout/pause behavior for the whole Builder pipeline: `config.builder.run_timeout` per Implementer/Auditor run, and `config.builder.limit_pause` (pause both threads when Claude's Pro usage limit is hit, resume after the pause window — CONTEXT §5 open question 3, assumed **yes**).

## Acceptance criteria
- [ ] `internal/builder/gate.go` implements the `builder.gate` job: no-op when `config.builder.enabled` is `false`; refuses repos not in `config.builder.repos` (same gate as M2-501/502/503 — do not name specific repos).
- [ ] Reads the audit verdict from `audit/N.M.md` (written by M2-503) and the corresponding `builds` row: verdict `pass` → marks the subphase gated/complete in the `builds` row and allows M2-505's PR step to consider the plan for completion once **every** subphase in the plan is gated `pass`.
- [ ] Verdict `fail` → creates fix tasks from the audit's findings and re-enqueues `builder.implement` for the same subphase with those findings appended as extra context (same "redo with note" shape used elsewhere, e.g. M2-401's `script.write` redo), incrementing an attempt counter on the `builds` row.
- [ ] After `config.builder.max_fix_attempts` failed attempts on the same subphase: stops retrying, marks the subphase/build `dead`-equivalent (per the queue's dead-letter pattern, ARCHITECTURE §5), and raises a Telegram alert — it must not loop forever.
- [ ] Enforces `config.builder.run_timeout`: when an Implementer or Auditor run (M2-502/M2-503) reports it hit this timeout (via the distinguishable result those jobs return), treats it as a failed attempt subject to the same `max_fix_attempts` bound above — a run that merely timed out is not automatically a plan-ending failure on its first occurrence.
- [ ] Enforces `config.builder.limit_pause`: when an Implementer or Auditor run reports a detected Claude Pro usage-limit hit, pauses **both** threads for the whole plan (not just the one that hit the limit — D7's parallelism means the other thread should also stop rather than race ahead unaudited) for `config.builder.limit_pause`, then automatically resumes and re-enqueues the paused work. Uses the existing global/per-agent pause mechanism (`settings` table pause flags, ARCHITECTURE §5) scoped to this plan/build, not a blanket daemon-wide pause.
- [ ] Table-driven tests next to the file: enabled/disabled gate, repo-not-listed rejection, pass → subphase gated, fail → retry with incremented attempt count, retries exhausted → dead + alert (no further retry), timeout treated as a bounded-retry failure, usage-limit hit pauses both threads and resumes after `limit_pause`.

## Notes
- CONTEXT.md §5 question 3 ("OK for Builder to pause when the Pro usage limit is hit and resume after reset?") is marked "Assumed yes" — this ticket implements that assumption as `config.builder.limit_pause`. If Mayank answers differently, this is the file to revisit.
- Which repos Builder may touch is still open (CONTEXT.md §5, question 1) and `config.builder.repos` is empty by default; `config.builder.enabled: false` also gates all of this off out of the box. Acceptance criteria and tests should exercise the gate logic against a fake/temp `builds` row rather than any real repo.
- How exactly M2-502/M2-503 signal "this was a usage-limit hit" vs. "this was an ordinary timeout" vs. "this was a real failure" is only loosely specified in those tickets' Notes (both flag the underlying `claude -p` CLI behavior as unconfirmed) — this job's tests should be written against whatever concrete result type/error those tickets land on, not against a guessed shape; coordinate with whoever implements M2-502/M2-503 rather than inventing a parallel signal.
