## Goal
`builder.gate` job that runs after each `builder.audit` completes and decides whether the plan may proceed to the next subphase, or whether the audit's findings must go back to the Implementer as a fix-and-retry loop (bounded by `config.builder.max_fix_attempts`, already in `config.example.yaml`). Also owns the cross-cutting timeout/pause behavior for the whole Builder pipeline: `config.builder.run_timeout` per Implementer/Auditor run, and `config.builder.limit_pause` (pause both threads when Claude's Pro usage limit is hit, resume after the pause window — CONTEXT §5 open question 3, assumed **yes**).

## Acceptance criteria
- [x] `internal/builder/gate.go` implements the `builder.gate` job: no-op when `config.builder.enabled` is `false`; refuses repos not in `config.builder.repos` (same gate as M2-501/502/503 — do not name specific repos).
- [x] Reads the audit verdict from `audit/N.M.md` (written by M2-503) and the corresponding `builds` row: verdict `pass` → marks the subphase gated/complete in the `builds` row and allows M2-505's PR step to consider the plan for completion once **every** subphase in the plan is gated `pass`.
- [x] Verdict `fail` → creates fix tasks from the audit's findings and re-enqueues `builder.implement` for the same subphase with those findings appended as extra context (same "redo with note" shape used elsewhere, e.g. M2-401's `script.write` redo), incrementing an attempt counter on the `builds` row.
- [x] After `config.builder.max_fix_attempts` failed attempts on the same subphase: stops retrying, marks the subphase/build `dead`-equivalent (per the queue's dead-letter pattern, ARCHITECTURE §5), and raises a Telegram alert — it must not loop forever.
- [x] Enforces `config.builder.run_timeout`: when an Implementer or Auditor run (M2-502/M2-503) reports it hit this timeout (via the distinguishable result those jobs return), treats it as a failed attempt subject to the same `max_fix_attempts` bound above — a run that merely timed out is not automatically a plan-ending failure on its first occurrence.
- [x] Enforces `config.builder.limit_pause`: when an Implementer or Auditor run reports a detected Claude Pro usage-limit hit, pauses **both** threads for the whole plan (not just the one that hit the limit — D7's parallelism means the other thread should also stop rather than race ahead unaudited) for `config.builder.limit_pause`, then automatically resumes and re-enqueues the paused work. Uses the existing global/per-agent pause mechanism (`settings` table pause flags, ARCHITECTURE §5) scoped to this plan/build, not a blanket daemon-wide pause.
- [x] Table-driven tests next to the file: enabled/disabled gate, repo-not-listed rejection, pass → subphase gated, fail → retry with incremented attempt count, retries exhausted → dead + alert (no further retry), timeout treated as a bounded-retry failure, usage-limit hit pauses both threads and resumes after `limit_pause`.

## Notes
- CONTEXT.md §5 question 3 ("OK for Builder to pause when the Pro usage limit is hit and resume after reset?") is marked "Assumed yes" — this ticket implements that assumption as `config.builder.limit_pause`. If Mayank answers differently, this is the file to revisit.
- Which repos Builder may touch is still open (CONTEXT.md §5, question 1) and `config.builder.repos` is empty by default; `config.builder.enabled: false` also gates all of this off out of the box. Tests exercise the gate logic against a fake/temp `builds` row (via `openBuilderDB`, the same sqlite-in-memory-file test helper `internal/builder`'s other tests already use) — no real repo, no real `claude`/git binaries except a fake `GitRunner` for the one `git show <branch>:<path>` read.

- **Consolidated open-question resolution (the ticket's main ask beyond the AC checklist).** CONTEXT.md §5 previously carried one open question (added by M2-503; M2-502's own ticket never separately recorded a matching one, so there was one row to resolve, not two — see `git show m2/M2-502:tickets/M2-502.md`, which only exports `ErrRunTimeout`/`ErrUsageLimit` for this ticket and says nothing about branch-landing conflicts) asking whether a non-fast-forward conflict landing the Auditor's commit onto the shared build branch should be retried by the Auditor itself or handed to M2-504. **Decision: the worktree doing the landing retries it — Gate never does.** Recorded as CONTEXT.md D25 (this commit), and the open-question row removed rather than left for a third ticket to re-ask. Reasoning:
  1. Both `implementer.go`'s `restoreMainRef` and `auditor.go`'s `fastForwardBranch` already return a **plain, non-`Permanent` error** on drift/non-fast-forward. The queue's own retry/backoff (ARCHITECTURE §5) re-runs that same job, which re-enters that same worktree, re-rebases onto the now-advanced branch tip, and tries landing again — this already *is* a retry loop, just one driven by the queue rather than by an explicit loop in application code.
  2. Only that worktree has the state a safe retry needs: the rebased tree, the exact commit being landed, and `merge-base --is-ancestor` proof of what "fast-forward" means *right now*. Gate has none of that — it only ever runs after a run has already finished (`audit.done` / a readable `audit/N.M.md` on the branch), so a landing conflict is resolved or re-attempted entirely before Gate is ever invoked. It is not a distinguishable outcome Gate could react to even if it wanted to.
  3. Moving this into Gate would mean giving Gate its own worktree and git-landing logic — duplicating `fastForwardBranch` for no behavioral difference, and widening `touches` past `internal/builder/gate.go`.
  This also means the timeout/usage-limit bounded-retry logic this ticket *does* own (AC bullets 4–6) is a genuinely different case from a landing conflict: those are signaled by `GatePayload.Outcome` (reusing `OutcomeTimeout`/`OutcomeUsageLimit`/`ErrRunTimeout`/`ErrUsageLimit` verbatim, per the ticket's "consume that signal" instruction), not by anything to do with git.

- **Known scope gap, called out rather than hidden**: `GatePayload.Outcome` is exercised directly by this ticket's tests (as the Notes above ask for — "against a fake/temp `builds` row"), but nothing in this repo yet enqueues `builder.gate` with `Outcome=timeout|usage_limit` automatically. `Subscribe` (mirroring `auditor.go`'s pattern) wires the normal pass/fail path off the existing `audit.done` event, which is sufficient because that event only fires once `Auditor.Run` has already produced a verdict. But `Implementer.Run`/`Auditor.Run` return `ErrRunTimeout`/`ErrUsageLimit` as a **plain queue error before any event or `builds` row is written** (confirmed by reading both files start-to-finish) — the marshalled `ImplementResult`/`AuditResult.Outcome` is in fact discarded by `queue.finalizeError`/`finalizePermanent`, which only persist `last_error`, not `result` (`internal/queue/worker.go`). So today, nothing in the repo can see that signal to forward it. Wiring `builder.implement`/`builder.audit`/`builder.gate` into `cmd/mayank2` doesn't exist yet at all (grepped — no `JobImplement`/`JobAudit`/`JobGate` registration anywhere outside `internal/builder`), so this is that future wiring ticket's job: wrap `Implementer.Handler()`/`Auditor.Handler()`, and on `errors.Is(err, builder.ErrRunTimeout)` or `ErrUsageLimit`, enqueue `builder.gate` with the matching `Outcome` instead of only letting the queue's generic backoff retry it blind. Flagging this explicitly (like M2-503 flagged its own `claude -p` CLI behavior as unconfirmed) rather than guessing at wiring code outside this ticket's `touches`.
