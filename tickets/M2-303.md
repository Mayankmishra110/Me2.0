## Goal
A `Publisher` for the X business account: uploads the short-form render as media and posts it via X API v2.

## Acceptance criteria
- [x] `internal/publish/x.go` implements `Publisher`: `Platform() string` returns `"x"`; `Publish(ctx, PublishRequest) (PublishResult, error)` is idempotent on `p.IdempotencyKey`.
- [x] Refuses to call the API unless the item's `approvals` row is `status = approved` (D5, F7).
- [x] Uploads video via the X media upload endpoint (chunked INIT/APPEND/FINALIZE for video, per X's media upload flow) reading the render directly from local disk (`data/media/renders/...`) — X's upload API accepts direct binary upload, so this publisher does **not** need the R2 presigned-URL step that Instagram/Facebook require; confirm this in Notes since it's a real difference between platforms in the same ticket batch.
- [x] Polls media processing status (`STATUS` check on the upload) until the video is ready before referencing its `media_id` in the tweet; a stuck/failed processing status fails the job (retryable) rather than hanging.
- [x] Posts the tweet via `POST /2/tweets` with the uploaded `media_id`, caption/text from `content_items` (respecting X's character limit — truncate or reject over-length text per format rules, don't silently cut mid-word).
- [x] Uses OAuth (1.0a user context for media upload, or OAuth 2.0 user context/app-only as required by the current X API v2 media + tweet endpoints — see Notes) with credentials loaded from `internal/secrets` (DPAPI vault) for the **business** account specifically — never the personal X account's credentials (COMPLIANCE §1: business and personal X **never** share posts or credentials, CONTEXT D12).
- [x] On success, records `external_id` (tweet ID) and tweet `url` in `publications`; on failure, wraps errors with `%w`, includes the X API error detail (not the token) in `last_error`.
- [x] Respects the X business daily cap (≤ 5 posts/day, COMPLIANCE §4); fails closed rather than posting past it.
- [x] Table-driven tests next to the file cover: idempotent replay, missing approval, media processing stuck/`failed` status, over-length caption handling, and a happy-path publish against a fake X API server (`httptest`).

## Notes
- **No live API access — best guess, not a live-docs verification.** This session (and the one before it on
  this branch) had no network access to check developer.x.com directly. Everything below is the best guess
  from model training knowledge, written down precisely so whoever has live docs access (or first real
  credentials) can check it fast:
  - **Endpoint paths implemented:** `POST /2/media/upload/initialize`, `POST /2/media/upload/{id}/append`,
    `POST /2/media/upload/{id}/finalize`, `GET /2/media/upload?command=STATUS&media_id=…`, `POST /2/tweets`.
    Training-era X docs describe X migrating chunked media upload off the old v1.1
    `POST /1.1/media/upload.json?command=INIT|APPEND|FINALIZE|STATUS` shape onto these `/2/media/upload/*`
    paths. **Re-check against live docs before this ever calls a real account** — if the v1.1 path turns out
    to still be required (or is required as a fallback), only `HTTPXAPI`'s URL-building needs to change; the
    `XAPI` interface and everything above it is shaped so that swap is isolated.
  - **Auth implemented:** every request (media upload AND tweet create) sends a single OAuth 2.0 user-context
    `Authorization: Bearer <access_token>` from `internal/secrets`/DPAPI, via the same `TokenSourceFor` /
    `oauth2.Token` shape `youtube.go` uses — no OAuth 1.0a HMAC-SHA1 request signing anywhere in this file.
    **Unverified:** whether the chunked media endpoints specifically still require OAuth 1.0a (X's media
    upload has historically lagged tweet-create endpoints in OAuth2 support). If live docs say 1.0a is still
    required for `/2/media/upload/*`, `internal/secrets.Store` needs a new shape (consumer key/secret + OAuth1
    token/secret, not just a bearer `oauth2.Token`) and a signer added — that is a real gap, not just a config
    change, and is out of this ticket's `touches` (`internal/publish/x.go` only).
  - **Unverified:** current free/basic/pro tier's exact posting and chunked-media-upload rate limits, and
    which tier the business account needs for video posting (free tier has historically been very limited or
    read-only for some endpoints). The ≤5/day cap below is our own product ceiling, not a substitute for
    confirming the account's real tier allowance.
- **No R2 (confirmed real platform difference, per ticket ask):** `Publish` reads the render straight off
  local disk (`os.ReadFile` under `data/media/renders/...`, path-confined the same way `youtube.go` confines
  `DataRoot`) and streams chunks to `/2/media/upload/{id}/append` directly. It never calls `internal/storage`
  or asks for an R2 presigned URL, unlike the Instagram/Facebook publishers (M2-301/302) which must hand Meta
  a public URL. Same `XAPI` interface would work unchanged if a presign step were ever needed, so this isn't
  load-bearing anywhere else.
- **Account naming convention for M2-403 (personal X publisher) to match:** `internal/secrets` keys tokens by
  `(platform="x", account)` — both the business and personal X publishers share `platform="x"`, so the
  `account`/`account_ref` string is the *only* thing that keeps their credentials apart. This file's
  `isPersonalXAccount(account string) bool` refuses (before any token lookup or API call) any account ref
  that is exactly `"personal"`, `"x-personal"`, or `"x_personal"`, contains the substring `"personal"`
  case-insensitively, or ends in `"-personal"`. **M2-403 must give the personal account an account_ref
  containing `"personal"`** (e.g. `x-personal`, matching CONTEXT D12's "X personal account" wording) so this
  guard rejects cross-account use by construction. This publisher's own business refs used in tests are
  `x-business`, `x-business-2`, etc. — any ref without `"personal"` in it is accepted, so config/wiring should
  standardize on an `x-business...` prefix even though nothing in this file enforces that positive form (only
  the negative "not personal" form is enforced, since that's the actual safety property D12 requires).
  Locked in by `TestX_AccountRefNamingConvention` (table-driven, `internal/publish/x_test.go`).
- **Caps:** product daily cap ≤ 5 posts/day (COMPLIANCE §4), enforced via `quotas` (`x:<account>`), fails
  closed (`reserveCap` before any API call; `queue.Permanent` on cap-exceeded so the job doesn't retry).
- **Caption:** 280 Unicode runes (`utf8.RuneCountInString`); truncates at the last whitespace boundary past
  the midpoint when possible; rejects (permanent, no API call made) when over-length with no usable word
  boundary, per the "don't silently cut mid-word" requirement.
- **Redaction:** `xRedact` strips `access_token=`, `Bearer `, and `oauth ` value spans from both outgoing
  request logs (never sent) and API error bodies before they reach `last_error` or `slog`, so tokens never
  land in `publications.error` or the log stream.
