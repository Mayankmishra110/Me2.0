## Goal
M2-116 registered 20 of SPEC §5's 27 job types in `cmd/mayank2/run.go` and deliberately left 6
unregistered: `research.brief`, `script.write`, `visuals.fetch` (the services exist — M2-203/204/207 are
`done` — but their packages exposed no queue adapter) and `blog.draft`, `blog.merge`, `blog.repurpose`
(handlers exist in `internal/blog` but `internal/config.Config` had no `Blog` section to construct their
options from). Until these are wired, the P2 content pipeline (scout → research → script → compliance →
voice → visuals → render) and the P4 blog pipeline (draft → merge → repurpose) cannot flow end to end in
the running daemon, even though every individual stage is built and unit-tested. Wire all six so `mayank2
run` registers every SPEC §5 job type exactly once.

## Notes
Written by crew-be, 2026-09-29, working from `origin/dev` (worktree `data/worktrees/m2-117`,
branch `m2/M2-117`).

**Chaining decisions and why**, since ARCHITECTURE §3.1's flow text names the job types but not their
exact payload shape:
- `research.brief`'s per-`content_id` `OutDir` subdirectory: `content.ResearchOptions.OutDir` /
  `ScriptOptions.OutDir` are each one fixed path set at construction (M2-203/204's own scope — those
  tickets only had to prove one `Run()` call worked, not concurrent queue jobs). `research.brief`/
  `script.write` both run on the `net` resource class, which `config.example.yaml` sizes at 2 concurrent
  workers by default — two real jobs sharing one `brief.json`/`script.json` path would silently
  overwrite each other. Fixed by having `handleJob` build a shallow per-job copy of the `Research`/
  `Script` struct with `OutDir` set to `<base>/<content_id>` before calling `Run` — no change to the
  already-`done` M2-203/204 `Run()` signatures or their existing tests.
- `script.write`'s `Allowed` formats fallback: a job payload has no way to reach a channel's configured
  format subset (`config/channels/*.yaml` `Formats`) without a filesystem lookup this handler doesn't
  otherwise need. When the payload's `allowed` is empty, `allCatalogFormatIDs()` (every id in
  `formats.Catalog`) is used instead — the picker's own G6 variety rule and topic-fit scoring still apply,
  it just isn't pre-narrowed to one channel's chosen subset. Flagged below as a CONTEXT.md follow-up rather
  than guessed silently.
- `script.write` → `compliance.script` payload: built as a real `compliance.ScriptPayload`/
  `compliance.ContentItem` Go value (internal/content now imports internal/compliance — no cycle,
  confirmed by reading compliance's own imports first), not a hand-built map, so the JSON shape can't drift
  from what `compliance.Engine.handleJob` actually unmarshals. `ScriptText` is the long variant's hook +
  beat text joined (falls back to short) — what G1/G2/G4/G7 need per `compliance.ContentItem`'s own doc
  comment.
- `blog.repurpose` had no handler at all, for a documented reason already in the repo:
  `internal/blog/repurpose_x.go`'s own comment on `JobBlogRepurposeXPersonal` explains that SPEC §5 lists
  one shared `blog.repurpose` name for all three M2-402/403/404 legs, that registering it from two sibling
  tickets built in parallel worktrees would collide (`queue.Register` panics on a duplicate job type — the
  same M2-116 guard this ticket's own acceptance criteria relies on), and that it used its own
  `blog.repurpose_x_personal` name instead "flagged for a follow-up doc/dispatcher ticket once all three
  legs exist." This ticket is that follow-up: `internal/blog/repurpose.go`'s `Dispatcher` owns the literal
  `blog.repurpose` name and calls the LinkedIn `Repurposer.Run` and `XRepurposer.Start` in-process — neither
  leg needed a second queue registration. The X leg's required `Source.Title` (not returned by
  `LoadSourcePost`, whose body has frontmatter — including title — stripped) falls back to the topic string
  already stored on the original content item at draft time (`loadTopicFromDB`, same package, already used
  by `blog.merge`). A leg failing does not fail the whole job as long as the other leg succeeded (each leg
  has its own independent approval gate); both failing does.
- `blog.merge` now optionally chains to `blog.repurpose` on a genuinely new merge (guarded by the same
  `idemKey` early-return that already makes `Run` idempotent, so a replayed merge never re-triggers
  repurposing). It does **not** chain to `blog.medium` (M2-404, already built with its own
  `RegisterHandler`/job type `blog.medium` — not part of SPEC §5's literal list and not one of this
  ticket's six): `medium.go`'s own `TelegramSender` interface needs a `*telegram.Client`, which
  `internal/telegram.Bot` doesn't expose publicly, and adding that accessor is outside this ticket's
  `touches`. Flagged in CONTEXT.md below rather than silently wired in a way that would make `blog.merge`
  fail at the `Enqueue` call for a job type nothing registers.
- Content agents never use Claude: `TaskResearch`/`TaskScript` (both `research.brief`/`script.write` use)
  were already routed in `internal/llm/llm.go` to free hosted tiers → local Ollama last resort, never
  Claude — confirmed by reading the router, not assumed. `blog`'s `TaskBlog` route is Claude — the one
  documented exception (CLAUDE.md, CONTEXT D13), unchanged by this ticket.
- `DASHBOARD_TOKEN`/telegram/OAuth-lazy patterns from M2-116 are untouched; `visuals.fetch`'s nil-`Stock`
  degrade and `Blog.Enabled()`'s off-by-default both follow the same CONTEXT D24 shape M2-116 already
  established for publish/analytics tokens.

### Open question added to CONTEXT.md §5
Two follow-ups from this ticket that are product/architecture decisions, not implementation gaps:
1. `script.write`'s per-channel `Allowed` formats subset (see above) — currently defaults to the whole
   catalog when a job payload doesn't carry it.
2. `blog.medium` wiring needs `internal/telegram` to expose a `*telegram.Client` (or equivalent sender)
   publicly so `cmd/mayank2/run.go` can construct `blog.Medium` and `blog.merge` can chain to it.
