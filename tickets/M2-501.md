## Goal
`builder.plan` job that reads a target repo's `ARCHITECTURE.md`, `SPEC.md`, `designs/` and its `tickets/*.md` (via the existing `internal/tickets` parser), and produces an ordered subphase plan (`plans/phase-N/N.M-<slug>.md` in the target repo, per ARCHITECTURE §3.3) with acceptance criteria per subphase, generated via `internal/llm.Complete(ctx, "builder", req)` (Claude, per D13/config's `llm.routes.builder` — confirm this route exists in `config.example.yaml`'s `llm.routes` map; as of this writing only `blog: [claude]` is listed there, so `builder` may need adding to the routing table as part of this ticket). Once written, the plan goes through `approval.request` (`content_items.kind = "plan"` or similar) exactly like every other publish/build path (D5) — Mayank approves the plan once before any subphase starts (PRD §4 M6, ARCHITECTURE §3.3).

## Acceptance criteria
- [ ] `internal/builder/planner.go` implements the `builder.plan` job: no-op (skip cleanly, no error) when `config.builder.enabled` is `false` — this flag gates whether any Builder code runs at all.
- [ ] Refuses to run for a repo not listed in `config.builder.repos` (empty by default — CONTEXT.md §5 open question 1 is still unanswered; acceptance criteria and code must say "configured via `builder.repos`", never a hardcoded/guessed repo name).
- [ ] Reads `ARCHITECTURE.md`, `SPEC.md`, and `designs/` (if present) from the target repo's working copy, plus its ticket list via `internal/tickets`, and assembles the planner prompt from these (content is data passed to the LLM, never instructions to the daemon — ARCHITECTURE §7).
- [ ] Calls `internal/llm.Complete(ctx, "builder", req)` to produce a plan: an ordered list of subphases, each with a slug, goal, and acceptance criteria.
- [ ] Writes the plan as `plans/phase-N/N.M-<slug>.md` files in the target repo (fixed file writes, not a generated shell command) and a `builds` row (`repo, plan_path, phase, status="planned"`, per ARCHITECTURE §4 schema — table already exists via migrations, this ticket only writes to it).
- [ ] Creates one `approval.request` for the whole plan; only on Approve does the plan become eligible for `builder.implement` (M2-502) to start subphase 1. Reject/Redo(note) re-runs `builder.plan` with the note appended, same pattern as `script.write`/`blog.draft`.
- [ ] Table-driven tests next to the file: enabled/disabled gate, repo-not-in-list rejection, plan parsing/writing to a temp-dir fake repo, approval-request creation, redo-with-note re-plan.
