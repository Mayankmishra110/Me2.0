## Goal
A `Publisher` for the Facebook Page (Reels/video) using the Meta Graph API and a page-scoped access token.

## Acceptance criteria
- [x] `internal/publish/facebook.go` implements `Publisher`: `Platform() string` returns `"facebook"`; `Publish(ctx, PublishRequest) (PublishResult, error)` is idempotent on `p.IdempotencyKey`, matching the check-before-call pattern used by the other publishers.
- [x] Refuses to call the Graph API unless the item's `approvals` row is `status = approved` (D5, F7).
- [x] Gets a temporary public URL for the render from `internal/storage` (R2 presigned GET, M2-213) for the video upload call — same reasoning as Instagram: Meta's video publishing endpoints take a hosted URL (`file_url`), not a multipart upload from this process.
- [x] Uses a **page-scoped access token**, not the user token — exchanges/loads the page token via `internal/secrets` (DPAPI vault) keyed by the Page ID; document in code comments that page tokens are long-lived but can be invalidated by a password change/permission review, and the publisher surfaces a clear "reauth needed" error (not a silent retry loop) when the Graph API returns an auth error.
- [x] Publishes as a Reel/video post to the Page feed via the Graph API video endpoint (`POST /{page-id}/videos` or the Reels-specific publish endpoint — see Notes) with title/description from `content_items`; sets the AI-disclosure and paid-partnership fields when the compliance report requires them (COMPLIANCE §1 Meta row).
- [x] On success, records `external_id` and post `url` in `publications`; on failure, wraps errors with `%w`, includes Graph API `error.code`/`error.message` in `last_error`, never logs the token.
- [x] Respects the Facebook daily cap (≤ 3/day per account, COMPLIANCE §4); fails closed rather than posting past it.
- [x] Table-driven tests next to the file cover: idempotent replay, missing approval, page-token auth failure surfaced distinctly from a generic API error, and a happy-path publish against a fake Graph API server (`httptest`).

## Notes
- Not fully certain whether the current recommended path for a Page-owned Reel is the general `/{page-id}/videos` endpoint with `video_state`/container semantics similar to Instagram, or a distinct Reels publishing endpoint — Meta has moved Reels functionality around Graph API versions. **Double-check the current official Meta docs for Facebook Page video/Reels publishing before implementing**; do not assume the Instagram container/publish two-step maps 1:1 onto Facebook.
- Verify current page-token acquisition flow (long-lived Page Access Token via `/me/accounts` after a long-lived User token) is still accurate, since Meta periodically changes token exchange requirements and required permissions (`pages_manage_posts`, `pages_read_engagement`, etc.).
- Same account-linkage note as M2-301: this Page is the parent of the Instagram Business Account, so confirm whether the same stored token can serve both publishers or if they must be fetched/stored separately in `oauth_tokens`.

### Independent qa+sec audit — 2026-09-28 (crew qa+sec)

Did not trust the prior `## Review` verdicts above at face value — re-read `facebook.go` end to end
myself, specifically grepping every place a raw Graph/rupload response or error gets parsed, logged,
or stored, per the audit brief (same class of check that caught M2-205's G7 gap).

**QA: changes** — 2026-09-28 — This ticket's own AC states publish failures "wrap errors with `%w`,
include Graph API `error.code`/`error.message`... never log the token." Found a path where that's not
actually guaranteed end-to-end — see SEC finding below. Everything else confirmed: `content.RequireApproved`
(facebook.go:113) runs before `lookupPublished` (116, idempotency) and both run before `reserveCap` (121),
`f.token()` (129), and `api.StartReel` (142, first Graph call) — idempotency lookup is genuinely before
the container-equivalent create call. `ErrReauthNeeded`/`ErrDailyCapExceeded` sentinel wiring traced and
confirmed correct (see below).

**SEC: changes — real gap, same class as the G7 finding (a check that looks wired but silently isn't,
in one specific path).**

`internal/publish/facebook.go` redacts Graph/rupload response bodies before parsing them **everywhere
except one path**:

- `fbDoJSON` (facebook.go:403-433), used by `StartReel` and `FinishReel`, redacts the body
  (`body = []byte(fbRedact(string(body)))`, line 413) **before** `json.Unmarshal` and before building
  any fallback error string. Safe.
- `HTTPFacebookAPI.UploadHosted` (facebook.go:477-504) does **not** use `fbDoJSON`. On HTTP ≥400 it
  unmarshals the **raw, unredacted** body into `{error:{code,message}}` (line 497:
  `_ = json.Unmarshal(body, &ge)` — `body` at this point has not been through `fbRedact`, unlike
  `fbDoJSON`'s line 413), then returns `fbWrapGraph(ge.Error.Code, ge.Error.Message)` (line 499) built
  from that unredacted message. Only the *other* branch of this same function (line 501, when
  `ge.Error == nil`) redacts.
- `Facebook.Publish`'s upload-error branch (facebook.go:148-152) computes a redacted `msg` for the
  `failPublication` DB write (`publications.error`, line 149-150) but then returns the **original,
  unredacted** `err` wrapped with `%w` (line 151: `fmt.Errorf("publish/facebook: upload: %w", err)`) —
  not the redacted `msg`.
- That returned error propagates through `Handle()` (line 342: `return nil, err`, unredacted) into
  `internal/queue`'s `finalizePermanent`/`finalizeError` (`internal/queue/worker.go:339,356,369`), each
  of which does `UPDATE jobs SET ... last_error=?, ...` bound to **`err.Error()` directly** — a real,
  plaintext DB column, not the DPAPI vault.

Net effect: if the Meta rupload endpoint ever echoes request content (a malformed `Authorization: OAuth
<token>` header it rejected, or the `file_url` it was given) back into its JSON `error.message` on a 4xx
response, that content lands **unredacted in `jobs.last_error`**, bypassing this product's own
"never log the token" rule — even though `publications.error` does get the redacted copy via the
separate `msg` variable. This is the one function in this file, and the only one across all four
platforms audited this pass, that diverges from the "redact body before any JSON parse or error
propagation" pattern used everywhere else (`fbDoJSON` itself, and Instagram/X/Pinterest's equivalents —
all confirmed clean this same audit).

The prior SEC pass above already flagged this generically as a non-blocking nit ("returned `%w` errors
not scrubbed (DB `error` is)") but did not pin it to a function/line or trace it to the `jobs.last_error`
DB write — this audit does, and upgrades it from nit to blocking because it is a concrete, live path to
a plaintext DB column, not just error-string cosmetics.

**Fix:** redact `body` before the `json.Unmarshal(body, &ge)` at facebook.go:497 (mirror `fbDoJSON`
line 413), and change `Facebook.Publish`'s upload-error branch (line 151) to return the redacted `msg`
(or `fbRedact(err.Error())`) instead of the raw `err`. To keep `errors.Is(err, ErrReauthNeeded)` working
through the returned error (the reason `%w` was used), redact *inside* `fbWrapGraph` before it builds
the sentinel-wrapped error, rather than redacting only the string handed to `failPublication`.

**Confirmed correct (unaffected by the above):** `ErrReauthNeeded`/`ErrDailyCapExceeded` end-to-end
wiring — `Handle()` (facebook.go:339) uses `errors.Is(err, ErrDailyCapExceeded) ||
errors.Is(err, ErrReauthNeeded)` → `queue.Permanent(err)` → `queue.IsPermanent` (`internal/queue/queue.go:267-270`,
`errors.As`) → `worker.go:279` `finalizePermanent` (no retry). A generic Graph error (code not in
{190,102,10,200,283}) is NOT wrapped in either sentinel by `fbWrapGraph` (facebook.go:395-401) and
correctly falls through `Handle()`'s `return nil, err` (unwrapped) to `finalizeError` (retry with
backoff) instead. Traced both directions, both correct.
